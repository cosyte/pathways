# @cosyte/pathways

## 0.0.2

### Patch Changes

- 2adffa2: Control one channel of a running engine: `pathways channel pause`, `resume`, `stop`, `halt` and `reload`, without restarting the others.

  - New command `pathways channel <pause|resume|stop|halt|reload> <name>`, with `--deadline` for `stop` and `halt` and `--json`. `pause` stops the source taking messages in while stored messages go on to delivery; `stop` also ends the channel's work after the message in hand, waits up to the deadline (30s by default) and reports what it left; `halt` cuts the delivery in flight off at once, leaving it pending to be sent again, flagged, after a `resume`; `reload` loads the channel's transform, its settings and the transform's `config:` blocks in a fresh worker and swaps them in between messages. A reload is refused, keeping the running transform, when the configuration is invalid or a `config:` value names an environment variable that is not set, the new transform throws as it loads, the channel is gone, a stop is still draining it, or the change is to the source, destinations, format or hooks (named, as needing an engine restart). Two reloads run one after the other, and a reload a stop overtakes (queued, or while its transform loads) is refused too. Two commands at once leave the source as the last one set: one that pauses or stops the channel while a resume is opening its source closes it again before it takes a message in. `--deadline` is at most 24 days, the longest wait a timer holds; a longer one is refused.
  - `pathways start` listens on a control socket: a Unix socket named by a hash of the project path in a `pathways-<uid>` folder it makes with mode 0700 (under `XDG_RUNTIME_DIR`, the temporary folder, or `/tmp`, within the socket path limit), or a named pipe on Windows. A stale socket is removed; a start that finds another engine answering there refuses and exits 1. One line of JSON each way, with a version, a 4 KB request limit and a 5s idle limit; replies carry states and counts, never content. `pathways channel` says `engine not running` when nothing answers.
  - Paused and stopped channels are kept in a new `channel_states` table (migration `0009-channel-states`, an expand step, a new table only, on SQLite and the four servers), read at the top of each pass by every engine on the database: a restart keeps a channel paused, and a command given to one engine reaches the others within one pass. Dropping the table with every engine stopped sets every channel running. The engine changes the channel before it stores the state, so a stop takes hold at the next message; a state the database does not store is put back, and the command is refused as `state-not-stored`.
  - Each command is written to the audit log as `channel-pause`, `channel-resume`, `channel-stop`, `channel-halt` or `channel-reload`, with the user the command reports, a refused one too (a channel the engine does not run among them); the socket folder, open to that user alone, is the trust boundary. On Windows the pipe's name can be guessed by another local user, a weaker boundary the how-to describes.
  - The health body gains each channel's `state` (`running`, `paused` or `stopped`); neither paused nor stopped changes the answer from 200.
  - API additions: `MessageStore` gains the optional `channelStates` and `setChannelState` (a custom store without them keeps a channel's state in the engine only, and a restart forgets it); `OutgoingMessage` gains an optional `signal`, aborted on a halt, which a custom destination may pass to its client; new exports `ChannelRunState` and `ChannelStateStore`. `AuditAction` gains the five channel actions. No caller needs to change.
  - New log events: `channel-state`, `channel-states-unread`, `channel-state-unstored`, `channel-reloaded` and `delivery-halted`.

- 71bc365: JSON Schemas for `pathways.yaml` and `channel.yaml`, and a `pathways validate` command.

  - Two new package subpaths, `@cosyte/pathways/schema/project.json` and `@cosyte/pathways/schema/channel.json`: JSON Schemas (draft-07) of the two files, which the build writes from the configuration's own schemas to `schema/` at the package root. They describe what you write (a duration as `5s` or a number of milliseconds), give each key a description an editor shows on hover, and restate the rules between keys that JSON Schema can state: one kind per source, destination, storage block and hook, `options` with `module`, a client `cert` with its `key`, TLS unless `plaintext: true`, and MLLP only with `format: hl7v2`. Each checks a subset of what `pathways start` checks: whatever start accepts, the schema accepts.
  - `pathways init` writes a `# yaml-language-server: $schema=` modeline at the top of the starter's `pathways.yaml` and `channel.yaml`, naming the schema by its path under `node_modules`, so an editor that runs the YAML language server completes and checks them once the project's dependencies are installed. A project made before this release can add the same first line; the docs page "Check configuration in an editor and in CI" shows it.
  - `pathways validate` checks a project's configuration as `start` does before it reads a secret, opens the database or listens: every key, the rules between them, the files they name, and that `encryption` is set. It prints a problem as `start` prints it and exits 3, or exits 0, so a project's CI can run it without secrets.
  - Nothing a caller must change: every configuration that loaded before loads the same way.

- 20b996c: A schedule per polled source, a deadline on each pass and on every delivery, and a way for a running source to say it lost its connection.

  - A `file` or `module` source may set `poll:` beside its kind: an interval such as `30s`, `onStart` for one pass at start, or a mapping with exactly one of `every`, `cron` (five fields, read with `timezone`, `UTC` by default) or `onStart: true`, and a `deadline` (`5m` by default). Without it, a source is polled every `pollInterval`, as before. `poll` on an `http` or `mllp` source, `timezone` without `cron`, a cron expression that is not five fields, or a time zone Node does not know is refused, naming the file and key. Cron expressions are read by croner, a new dependency (MIT, no dependencies of its own).
  - Each source's pass runs beside the engine loop, so a source that hangs holds up no other channel. A pass never overlaps itself: one that comes due while the last `poll` call has not returned is skipped and logged as `poll-overlap`. A pass past its deadline is cut off and logged as `poll-deadline`: the signal handed to `poll` aborts, and each later `sink.receive` of that pass rejects with the code `POLL_DEADLINE` before it stores anything, so the source keeps the message. A pass missed while the engine was down, or while the last one ran, is not made up. When `pathways start` stops, a pass under way finishes storing what it is storing and takes nothing more in, its `poll` call is waited for up to its deadline, and what the sources took in goes on through the transform and delivery before it exits, as before. A `poll` that rejects once its pass is cut off, such as one that handed the signal to its client and got an `AbortError`, is part of the cut and not an error; one that rejects before still ends the run with its error. `pathways start --once` polls every source once, whatever its `poll`.
  - Every delivery attempt (connecting, sending and the receiver's confirmation) runs under a deadline: an HTTP destination's `timeout` plus a second, twice an MLLP destination's `ackTimeout` plus a second, and a `file` or `module` destination's new `timeout:` key, `30s` by default. At the deadline the destination's `signal` aborts and the attempt is retried as any other failure, with the code `DELIVERY_TIMEOUT`, not flagged as a possible duplicate, though the receiver may have the message already, so a receiver should drop duplicates by `messageId` and `seq`. A custom destination that took longer than 30 seconds before now needs `timeout:` set in its block. The liveness bound counts each destination's deadline, so with the defaults a project with file or module destinations has a bound 25 seconds longer than before.
  - API additions: `MessageSink` gains the optional `sourceDown(code)` and `sourceUp()`, which the engine's sink always has. `sourceDown` marks the channel's source `down` on the health endpoint (503) and readiness, logs `source-lost`, sends the hooks `source-down` with `name: "SourceDown"`, and returns how long to wait before reconnecting (1 second, doubling to 5 minutes); `sourceUp` logs `source-regained` and sends `source-up`. A code that is not letters, digits and `_.:-` (at most 64) is kept as `UNSPECIFIED`, so no error text reaches a log. `SourceConnector.poll` takes an optional second argument, the pass's `signal`. Code written against these types keeps compiling unchanged.
  - Each output's `messageId` and `seq` stay the same on every attempt and resend; the delivery docs now say how a receiver can use the pair to drop a copy.

- 59d9927: A published, signed container image, and a starter `Dockerfile` that builds a project's own image on it.

  - Each release publishes the image to `ghcr.io/cosyte/pathways`, tagged with the version, for `linux/amd64` and `linux/arm64`, with an SBOM and build provenance attached. The release pushes it by digest alone, signs that digest with cosign keyless signing, pulls it back and checks the signature and both platforms' SBOM and provenance, and only then adds the version tag, so a version tag always names a signed, checked image. The image is built from the same commit and lockfile as the npm package, not from the npm tarball. There is no `latest` tag. Check an image with `cosign verify ghcr.io/cosyte/pathways@sha256:<digest> --certificate-identity https://github.com/cosyte/pathways/.github/workflows/release.yml@refs/heads/main --certificate-oidc-issuer https://token.actions.githubusercontent.com`.
  - The image stays as it was: the `pathways` command and the four database drivers. Extensions and cloud packages go in a project's own image.
  - `pathways init` now also writes a `Dockerfile` and a `.dockerignore`. The `Dockerfile` builds the project's image FROM the Pathways image of this version, by digest (the build stops until the digest is added to its `PATHWAYS_IMAGE` line), installs the project's `dependencies` in a build stage, copies in `package.json`, `pathways.yaml` and `channels/`, and runs `pathways validate` and `pathways test`, so an image whose channels do not validate or whose tests fail is never made. The `.dockerignore` keeps the development key, the database, the message folders and `node_modules` out. A new how-to, "Deploy the image", says how to ship each change as a new image tag and roll back to the tag before.
  - `pathways init` lists the two new files in what it prints. Nothing for an existing project to change; a script that compares `init`'s list of files with a fixed one gains `.dockerignore` and `Dockerfile`.

- 2729c6a: The delivery deadline costs less per attempt, and a cut pass's own error is logged.

  - Each delivery attempt is still cut off at its destination's deadline, as before, but no longer makes a timer of its own: the attempts of one pass share one timer, and each makes one `AbortController` where it made two and an `AbortSignal.any`. The signal a destination is handed aborts as before, with the halt's reason on a halt. Nothing a caller must change.
  - croner, which reads `poll` cron expressions, is loaded on the first cron expression the configuration or the schedule reads, rather than when `pathways start` loads, so a project without one never loads it.
  - A polled source's `poll` that rejects after its pass was cut off, with an error other than the cut's own (the signal's reason, an `AbortError`, or the sink's `POLL_DEADLINE` refusal), was swallowed with no log line. It is now logged at warn as `poll-failed-after-cut`, with the error's `code` and never its text. The run still ends as the cut ends it.

- b39df91: A new `storage.content` setting decides what is kept of a message's content. `keep`, the default, changes nothing. `dropAfterDelivery`, in `pathways.yaml`'s `storage:` block or a channel's own `storage:` block, deletes a message's body and the bodies of its deliveries in the same transaction that records its last delivery as delivered, for teams that must keep as little patient data as they can.

  - Only the deliveries of the message's current generation count. While any of them has failed or waits to be tried again, every body is kept, so the message can still be replayed or resent.
  - The metadata stays: ids, times, statuses, attempts, the size, the possible-duplicate flag, and a SHA-256 hash of the body as received, which the engine works out as it stores a message for such a channel. `pathways messages show` prints the hash and when the content was dropped. Each delivery's last error text goes with the bodies. The hash has no key and is stored unencrypted, even with encryption at rest, so someone who can read the database and guess a message's exact text can confirm it passed through: protect it as you would the content.
  - `pathways replay` and `pathways replay --resend` refuse such a message with `content-dropped`, changing nothing; `pathways rekey` skips it; retention leaves it, so its metadata is kept.
  - The engine logs `content-dropped` with the channel, the message and the delivery.
  - Schema step `0008-content-drop` (expand) adds two columns to `messages` that may be null, `content_hash` and `content_dropped_at`. It only adds, and has no rollback step. The next release applies it with `0005` to `0007` and `0009` when it opens a 0.0.1 database.
  - On SQLite, opened with `secure_delete`, a test drops a message holding a synthetic marker and finds no copy of it in the file. The write-ahead log still holds the received body until it is checkpointed; a second test finds the marker there with the store open, empties the log beside it with `PRAGMA wal_checkpoint(TRUNCATE)`, and then finds no copy in either file. A database server can keep the old bytes for a while (dead rows, undo and transaction logs, backups and replicas); the storage page says what each keeps, with a link to the vendor's documentation for each claim.
  - New in the API: the optional `MessageStore.markDeliveredAndDropContent(deliveryId, epoch?)`, the optional `contentHash` on `StoreReceiveOptions`, and the optional `contentHash` and `contentDroppedAt` on `MessageSummary`. `RefusalReason`, the reasons of `RequeueResult`, and `ActionRefusal` gain `content-dropped`. A custom store needs no change unless a channel asks for `dropAfterDelivery`: then it implements `markDeliveredAndDropContent`, and `pathways start` refuses that channel on a store without it. Code that switches over `RefusalReason` or `ActionRefusal` gains one case to handle.
  - A `storage:` block may now name `content` alone, which keeps the default SQLite file.

- 25643d1: Dry-run destinations, and a `pathways verify` command that shows what a newer Pathways or a changed transform would send differently, before it sends anything.

  - A destination block takes `dryRun: true` (or an environment reference, `dryRun: { env: NAME }`), and `pathways start --dry-run` runs every destination dry. `DestinationConfig` gains an optional `dryRun`, beside its `retry`. Each output is transformed and stored as before, and its delivery is marked with a new status, `dry-run`, in place of the send. No connector is built for such a destination, so no TLS file, secret or module is read and no connection is opened; start does not ask a secret provider for its secrets either, so a missing or expired one does not stop a dry start. The engine logs `dry-run` for each, and once at start with `--dry-run`; at start it also names, by index under each channel, the destinations that run dry (`dry-run-destinations`), so one that sends shows by its absence. When `dryRun` is read from an environment variable, setting that variable to `false` makes the destination send for real, and the audit log does not record that change. Turning dry run on marks a destination's whole pending backlog `dry-run`, deliveries queued or retrying before too, so the engine warns at start (`dry-run-pending`, with the channel's pending count) when there is one; `pathways replay <id> --resend` sends such a message later.
  - `DeliveryStatus` gains `dry-run`. The delivery counts (`deliveryCounts`, now typed by a new `DeliveryCounts`, the `DeliveryTally` of a listed message, and the health endpoint's body) carry a `dry-run` key only once a delivery ran dry, so a project that never runs dry reads exactly as before, and a custom store's `deliveryCounts` needs no change. `MessageState` and `MESSAGE_STATES` gain `dry-run`: a transformed message whose deliveries are all done and at least one ran dry. `pathways messages --status dry-run` lists them, `pathways status` counts them when there are some, and retention deletes them as it deletes delivered ones.
  - `MessageStore` gains an optional `markDryRun(deliveryId, epoch?)`, fenced like `markDelivered`. A custom store without it keeps working; `pathways start` refuses a project with a destination that runs dry on such a store, with a configuration error that names the channels.
  - `pathways verify [--channel <name>] [--since <time> | --ids <id,...> | --samples <dir>] [--json]` runs inputs through the project's transforms (point `-C` at a candidate copy) in the same workers the engine uses, and compares each output, byte for byte, with the one recorded: the outputs stored for a message (from the last 24 hours by default), or a sample's `.expected` file. It prints per channel and destination how many were the same, different or failed, and where each difference starts, by HL7 v2 field path (`PID[1]-8`), JSON pointer, or byte offset, never by value. It exits 1 on any difference or failure, 4 for a message id that does not exist. It reads stored messages decrypted in memory, writes each to the audit log before reading it, and writes nothing to the message or delivery tables; with `--samples` it opens no database. On SQLite, where the database file does not exist, it stops and creates none. Each transform reads its channel's `config:` as the engine does, and a stored message runs with its own id as `ctx.messageId`. It applies no schema step, as `pathways start --no-migrate` does, so a candidate on a newer Pathways never changes the schema under the running engine; a database that lacks a step the candidate needs is refused, naming both versions.
  - The audit actions (`AUDIT_ACTIONS`, `AuditAction`, `AuditEventAction`) gain `verify`.
  - A caller that matches every `DeliveryStatus`, `MessageState` or audit action exhaustively adds the new values, and one that reads the counts of a project that runs dry reads `dry-run` as optional. Nothing else changes for a project that does not set `dryRun`.
  - The Upgrade Pathways page gains how to check a new version before it sends: a candidate project, `pathways verify`, and destinations that run dry.

- d60fa20: One engine per database, enforced: `pathways start` now takes an engine lease before it opens a source, and every write that records the engine's work is fenced by the lease's epoch. Before, a second engine on the same database ran beside the first, and both could send the same delivery.

  - The lease is a row in a new `leases` table: the holder's node id and host, since when, an epoch that rises on every acquisition, and an expiry judged by the database's clock in the same statement that takes or renews it. Migration `0006-leases` only adds the table, so it is safe while deliveries are in flight; it has no rollback step, and dropping the table with every engine stopped undoes it.
  - A second `pathways start` on the same database exits 1 and names the holder (node, host, since, epoch, time left), never a URL. The holder renews every third of `lease.ttl` (15s by default, a new `lease` block in `pathways.yaml`). A renewal that is refused, fails, or comes later than the lease lasts by the holder's monotonic clock, or a fenced write that changes nothing, stops all sending and taking in at once, logs `lease-lost` and exits 1. A clean stop frees the lease; a killed engine's lease is taken by the next start after the time to live.
  - `pathways start --standby` (or `lease: { standby: true }`) waits on a database server without a lease, a listener, a folder or a body read, answers health with 503 `standby`, and takes over within the time to live plus one renewal interval plus its start. It is refused on SQLite.
  - New commands: `pathways lease status` prints the holder; `pathways lease release --force` frees the lease of an engine whose host is gone, and writes a `lease-release` entry to the audit log. The operator commands run beside a held lease as before.
  - API addition for custom store implementers: `MessageStore` gains the optional `acquireLease`, `renewLease`, `releaseLease` and `leaseHolder`, and `completeTransform`, `failTransform`, `markSending`, `markDelivered`, `scheduleRetry` and `failDelivery` take an optional last `epoch`: given one, the write changes its row only while the `engine` lease carries that epoch, and otherwise rejects with `LeaseLostError`. A custom store without them needs no change, but its engine runs unfenced: a second engine on the same store is not refused and no write checks an epoch; it logs a `lease-unsupported` warning at start, and cannot run a standby. New exports: `ENGINE_LEASE`, `LeaseLostError`, and the `LeaseClaim`, `LeaseClaimant`, `LeaseHolder` and `LeaseStore` types. `HealthReport.status` gains `standby`, and the audit actions gain `lease-release`.
  - Not covered: the send itself cannot be fenced, which at-least-once delivery allows. An engine paused after a send and before recording it can mean that one delivery is sent once more, flagged as a possible duplicate. An engine paused after writing the send marker and before the send lets the engine that takes over send first, flagged, and the paused one second, unflagged, before it finds its lease gone. With `resendFlag: false`, or in the few seconds after `pathways lease release --force` on an engine that is still running, a duplicate can go out unflagged.

- 188a905: Faster and leaner on large messages, with the same outputs: every transform output, ACK, stored row, delivered file and log line is unchanged on a corpus of 705 synthetic inputs across every format.

  - `@cosyte/hl7` 0.1.9, `@cosyte/fhir` 0.1.9, `@cosyte/x12` 0.1.11, `@cosyte/ccda` 0.1.6 and `@cosyte/mllp` 0.1.7. Under the default 256 MB memory cap, the transform worker now carries a dense HL7 v2 result report of up to about 5 MiB, where it carried about 2 MiB. Writing an HL7 v2 message back out still builds its whole parsed tree, about 44 times its size, so a channel that takes larger dense messages needs a larger `memory`.
  - Importing `@cosyte/pathways` no longer loads `@cosyte/hl7`: `defaultAckBuilder` loads it on its first ACK, as the same module an `import` of it gives, so a header you parsed with `parseHL7` is accepted as before.
  - A `json` channel checks its numbers in one pass over the body instead of through a reviver on every value. It accepts and refuses exactly the bodies it did, with the same codes.
  - SQLite prepares each statement once per connection instead of on every query.
  - The engine hands a body from stage to stage, or frees it once a stage is done, instead of copying it: encryption and decryption write into one buffer, the body moves to the transform worker and its outputs move back, and the file source and destination free a body once it is stored or written. A text payload the engine only passes through is now held about once in its own thread, where it was held about nine times. A custom store, source or destination sees no change: a body it is handed or hands over is never freed or moved.

- c3272c1: Any setting in `pathways.yaml` and `channel.yaml` that holds one value can now be read from the environment, so one image with the same YAML serves staging and production.

  - Public API addition: the `{ env: NAME, default? }` reference, accepted in place of every scalar setting (ports, hosts, durations, sizes, booleans other than `plaintext`, paths, URLs, choices such as `onStoreFailure`, key ids, each event in `events`, an HTTP source's paths, methods and fixed response). The variable is read when the configuration is loaded and its value is checked by the same rule as a value written in the file; `default` is used when the variable is unset or empty. A problem names the file, the key and the variable, never the value. Only the variables the files name are read: there is no prefix scan and no `${VAR}` substitution. Secrets keep their meaning of `{ env: NAME }`: a reference read at start, never resolved into the configuration.
  - Public API addition: `storage.kind`, one of `sqlite`, `postgres`, `mysql`, `sqlserver` or `module`, which picks the block used, so one file can hold a block per deployment. The blocks it does not name are still checked.
  - Public API addition: `pathways validate --print` prints the configuration as `start` reads it, as JSON, with each setting the environment gave listed under `environment` with its variable, and secrets as references.
  - The audit log's `config` entries add `env`, each key read from the environment and its variable (`health.port=HEALTH_PORT`), never a value. A file that starts or stops reading a variable is recorded as changed. A value changed only in the environment, with the files the same, is not audited.
  - `plaintext` is never read from the environment, nor are `encryption: none` and `auth: none`: turning TLS, encryption or authentication off stays in the file. `validate --print` shows the query string of a URL read from the environment as `?(hidden)`.
  - The JSON Schemas accept the reference wherever a scalar goes, and describe it.
  - Nothing a caller must change: every configuration that loaded before loads the same way. A mapping with an `env` key where a scalar goes was refused before and is a reference now.

- 1d4c81b: Named fault points for crash tests, and the engine and operator tests on every database.

  - The engine, storage and file source now mark eight points where a crash test can stop a real `pathways` process: `after-store-before-ack`, `after-transform-before-complete`, `after-send-before-record`, `mid-requeue`, `before-claim-move`, `after-claim-move`, `after-claim-flush` and `mid-move-back`. They exist only in the source the tests run. The published build leaves them out: each point is a function that does nothing, and no built file reads the test-only variable `PATHWAYS_TEST_FAULT_POINT`, so setting it in a deployment, to any value, changes nothing. The tarball smoke checks this on Linux, Windows and macOS. Nothing a caller must change, and no export is added.
  - The crash tests kill the process at each point, on SQLite and on each database server, and check that after a restart no message is lost, each delivery is made at least once, a delivery cut off after its send goes out again flagged, a replay cut off half written leaves nothing behind, and a clean restart sends nothing again. An operator's resend racing a delivery is tested under each server's default isolation level.
  - The engine, replay, rekey, retention and audit log tests now run on PostgreSQL, MySQL, MariaDB and SQL Server as well as SQLite, each test on a database of its own, and the image is now also checked against MariaDB.

- d3f268d: The file source and destination run over one internal file system interface, a step toward remote file locations.

  - The file source's claim, order, idempotency and recovery steps now run over one internal interface (list, stat, read, a write through a temporary name, rename, remove and make a folder) with three capability flags (a rename in one step, a rename that never replaces a file, a listing that shows every change at once), and each kind of location brings its own claim rule. A folder on this machine is the first, and the only one so far; it behaves exactly as before.
  - The docs page "Read and write message files" gains a table of the claim rule for each kind of location.
  - Nothing a caller must change: no configuration key, export or log event changed.

- 48c6456: A file the source refuses after a move goes to its held name before it is linked back, so a crash part way never leaves it stored twice.

  - A file the file source moved that turns out not to be the one it checked now moves first into `.claimed/` under a `refused-` name, where no pass reads, and goes back where it came from by a hard link and an unlink of that name. Before, it was linked back straight from the claim folder: a crash between the link and the unlink left it under two names a pass reads, and the next start stored it twice. Now a crash at any step leaves it under one such name at most.
  - When the unlink of the held name fails after the file is back, the source logs `ESTALE`, as for any file it put back, and the held name stays in `.claimed/`, where nothing reads it. Before, it logged `ERR_PATHWAYS_FILE_HELD`. Nothing a caller writes needs to change.

- 76c6245: The file source never overwrites a file when it moves one back, and bounds the time its patterns take in one pass.

  - A file the source moved that turns out not to be the one it checked (a folder on its path swapped for a link) goes back where it came from by a hard link and an unlink, never by a rename, so it never replaces a file put there since. One that cannot go back waits in `.claimed/` under a `refused-` name, is logged with `ERR_PATHWAYS_FILE_HELD`, and is never stored, by this run or a later one. When even the move to that name fails, it is logged the same way and waits in the claim folder: the run that refused it never stores it, and the next start does. Such a file is never taken while the source runs, wherever a later swap leaves it.
  - Before its first claim, the source checks that the folder's file system keeps a file's id when it moves. On one that does not, as FAT and exFAT can, it claims nothing and logs `source-read-failed` with `ERR_PATHWAYS_FILE_ID_UNSTEADY` on each pass, rather than refusing every file it moved.
  - One pass spends at most 500 ms running `include` and `exclude` patterns. Paths it has no time left for wait for the next pass, longest-waiting first, and a path's result is kept while its file is there, so each path is matched once rather than on every pass. Nothing a caller writes needs to change.

- 656d04e: Options for the file source: which files it takes, from where, how many, in what order, when a file is finished, and where a file it cannot take goes.

  - New keys under `source.file`: `include` and `exclude` (globs, or `{ regex }` of at most 256 characters, matched on the file's path from `dir` with `/` on every system), `recursive`, `ignoreDot`, `minSize`, `maxSize`, `maxPerPoll`, `sortBy` (`name` or `mtime`), `stable`, `doneFile`, `errorDir` and `readTries`. The JSON Schema for `channel.yaml` describes each. Each takes an `{ env: NAME, default? }` reference in place of its value, as every other setting does, and so does each glob and each `regex`.

  - The check that a file is still inside the source folder now runs in the file source for every kind of location, rather than in each location.
  - The docs page "Read and write message files" gains "Read and write over SFTP", and the configuration reference and the codes page list the new keys and codes.

- b5b2b0d: The transform context: a transform's second argument, `ctx`, with the message's source facts, its id and run, and a configuration map.

  The public additions:

  - `Transform` and `TransformFor` take `(message, ctx?)`. `ctx` is a `TransformContext`: a frozen plain object built for each message in the transform's worker, holding `messageId`, `attempt` (1, then one more per replay or resend), `source`, `config` and `meta` (always empty in this release).
  - `ctx.source` is a `SourceFacts`, by the kind of source, each with `receivedAt`: a file source's `name` and `size`; an HTTP source's `method`, `path`, `remoteAddress` and the `headers` its new `contextHeaders` key lists (`Authorization`, `Proxy-Authorization` and `Cookie` are refused there and never passed); an MLLP source's `remoteAddress` and, over mutual TLS, `tlsPeerSubject`, the common name of the sender's certificate; a custom source's `facts`, what it passes as the new `source` option of `sink.receive`, a map of plain JSON values (anything else is refused with `INVALID_SOURCE_FACTS` before the message is stored), copied at the call so the source may reuse its object. Any header `contextHeaders` lists other than those three is passed as it came, an API key header included. The facts are kept in memory until the message is transformed, for at most 4,096 waiting messages a channel, and are not stored, so `ctx.source` is `undefined` for a message taken in before the engine last started, for the oldest of a longer backlog, on a replay, and under `pathways test`.
  - A `config:` block in `pathways.yaml` and in `channel.yaml`, the channel's replacing the project's key by key, with its JSON Schema. Each `{ env: NAME }` in it (or `{ env: NAME, default: value }`) is read in the engine's process when it starts, and by `pathways test` and `pathways replay`, never when the configuration loads; a variable that is not set and has no default stops the start with a problem naming the file, key and variable, never a value. `ctx.config` is typed by the exported `TransformConfig` interface, which a project fills in by declaration merging.
  - New exported types: `TransformContext`, `TransformConfig`, `SourceFacts`, `FileSourceFacts`, `HttpSourceFacts`, `MllpSourceFacts` and `ModuleSourceFacts`.

  Nothing a caller must change: a transform that takes one argument, and every `Transform` and `TransformFor` type, compile and run as before. A project that already used a top-level `config:` key in `pathways.yaml` or `channel.yaml` could not have loaded before, since both refused unknown keys.

- e338241: Windows and macOS fixes found by running the suite natively on both:

  - A transform or extension module reached through a link (macOS's temporary folder is one) now
    gets the line it threw at in its failure, as `transform.ts:2:9`: Node names a module by its real
    path, and only the configured path was matched.
  - Configuration problems name files with `/` on Windows too, as `channels/adt/channel.yaml`, the

  - `pathways init` says on Windows that the key file's mode does not keep it private there: the

## 0.0.1

### Minor Changes

- 758e76f: The file source deletes each file once its message is stored, encrypted, instead of moving it into
  `processed/`. A run that stops between storing a file and deleting it stores that file once on
  restart, not twice. Keeping a plaintext copy in `processed/` is now the `keepProcessed: true`
  setting, off by default, and the engine warns once at start for each channel that turns it on.
  The Docker image carries every database driver: pg, mysql2, tedious and tarn.

### Patch Changes

- 726e707: A configuration problem about the project folder itself names it `.`, as every other path in a
  problem is named relative to the project, instead of printing the full path the caller typed.
- 9a165ee: The file source takes a file whose name is as long as the file system allows: a claimed file's
  name is a fixed-length claim id and as much of the end of its own name as fits in 255 bytes, and a
  `processed/` copy's name fits the same way. The moves that claim a pass's files are flushed to disk
  before any of them is stored, so a power cut cannot put a stored file back in the folder to be
  stored again. Each channel claims into `.claimed/<channel>/`, so two channels that read one folder
  never finish each other's files.
- 5c06538: The file source works on Windows. Windows cannot flush a folder to disk, so there each pass flushes
  every file it claims, under its claimed name, before it stores any of them, in place of the
  folders Linux and macOS flush. On Windows a file is opened to write before it is claimed, so a
  read-only file stays where it is and is reported as a read error. Linux and macOS are unchanged.
- 726e707: The engine ignores a message a transform posts itself from its worker thread. Before, a transform
  that posted `null` or `undefined` through `parentPort` threw in the engine's own thread, and only
  the worker's reply for the message now settles it.
