# @cosyte/pathways

## 0.0.5

### Patch Changes

- cca9c3e: Each delivery keeps its own queue time, so the oldest pending age per destination no longer restarts, and the health body and `/metrics` hold one set of reads on a database that hangs.

  - Schema step `0017-delivery-queued-at` adds a `queued_at` column to `deliveries`, set when a delivery is queued (a transform, a replay or a resend) and never moved by a retry, a failure or a clear. It is an expand step, applied at start: a column that may be null, with no default and no index, so it changes no row and is safe while deliveries are in flight. Its `down` drops the column and the step's record again.
  - `pathways_oldest_pending_age_seconds`, and `oldestPendingSince` in what `destinationQueues` returns, now count from that time. Before, they counted from the message's last update, so an operator clearing a failed delivery of a message restarted the age of its deliveries still pending at other destinations. A delivery queued before the step, or by an older Pathways on the same database, counts from its message's last update as before.
  - The health body waits at most 5 seconds for its store reads, as readiness does. A database that hangs now answers 503 with `storage: "unreachable"` and each channel `unknown`, rather than a request that hangs. While a set of reads has not ended no new set starts: a request in its first 5 seconds shares it, and a later one answers unreachable at once.
  - The `/metrics` store reads stay marked in flight until every read has ended. Before, the first read to fail cleared the mark while another channel's read still hung, so a new set could start beside the hung one.
  - The logs page says that an error thrown from a destination connector's send is retried and only its code is stored, where a transform's error fails the message, and that `console.error` and `console.warn` write to standard error. The hl7-to-fhir example's page says the patient in `a04.hl7` was set by hand.
  - What a caller must change: nothing. A custom store's `destinationQueues` may go on reporting the message's last update; a tool that reads the `deliveries` table by column sees one more.

- a7ad416: The docs say what is safe to log from a channel, and no example prints a value that identifies a person or a whole message.

  - A new section of the logs page, "What is safe to log from a channel": log `ctx.messageId`, `ctx.attempt`, the channel's and the destination's names, counts, sizes and codes; never the message, an output or a body, a segment, a field that identifies a person, `ctx.source`, `ctx.config`, `ctx.meta` or an error's own text. It says how each way of writing behaves: `ctx.logger` in `onStart` keeps a code and numbers only (a code is still words the script chooses, so never build one from the message), `console` in a transform writes to the process's standard output unfiltered, and a thrown error's text is never logged or printed. That text is stored with the message, encrypted when the store is encrypted and in the clear under `encryption: none`; a channel that stores nothing keeps none. So an error's message must never carry a value from the message.
  - Two samples in the reference that printed counts named `messages` now read them into a variable, and the samples that named an operator by a person's first name now use `ops`.
  - What a caller must change: nothing. No code, type or output changes.

- 089c186: A scrape of `/metrics` no longer hangs on a database that hangs.

  - The store reads behind the gauges now wait at most 5 seconds, as long as the readiness check waits. A database that neither answers nor fails in that time reads as `pathways_store_up 0`, with `pathways_store_latency_seconds` at 5 or more, and the store gauges are left out, so the scrape answers and the documented store-down alert can fire. Before, the scrape waited on the database for as long as it hung, and the collector saw a failed scrape rather than a store that is down.
  - Reads that time out are left running. A set of reads counts as in flight from when it starts until every read in it has ended, and while it is in flight no new set starts: a scrape shares its reading, and once it is 5 seconds old answers `pathways_store_up 0` at once, with the latency counted from when the hung set began. The readiness check does the same with its storage read, however often it is asked. So a database that hangs holds one set of metrics reads and one readiness read, not a new one every few seconds that would queue behind it and run ahead of message processing when it recovers.
  - The metrics docs say what ends a read that hangs on each database, and that the store gauges are absent, not 0, while the store is down, so the queue alerts go quiet and the store-down alert is the one that fires.
  - The help text of `pathways_store_up` and `pathways_store_latency_seconds` now names the 5 seconds.
  - What a caller must change: nothing.

- 1597ef9: An empty body is now stored on SQL Server wherever one is written, as receive already stored it.

  - A message one channel hands to another (a `channel:` destination or `ctx.route`) with an empty body, and a transform output that is empty, were bound to SQL Server as an empty buffer, which the server refuses: the hand-off or the transform's result failed and its transaction was rolled back. Both are now written as the empty binary literal `0x`, as receive writes an empty body.
  - `pathways rekey` (through `Store.replaceContent`) now also replaces a row whose stored body is empty on SQL Server, and writes an empty body when that is what it keeps; before, the comparison or the write bound an empty buffer and failed.
  - A non-empty body is written as before, and the other databases are unchanged.
  - What a caller must change: nothing.

## 0.0.4

### Patch Changes

- fbc2b57: Batch reading for the file and HTTP sources: one file or request body cut into many messages, each stored on its own.

  The public additions:

  - `batch:` on `source.file` and `source.http` in `channel.yaml`, with its JSON Schema: `split: hl7 | lines | delimiter`, and `delimiter` for the last. `hl7` cuts with `@cosyte/hl7`'s `readMessages` (batch envelopes, bare messages one after another, MLLP frames); `lines` at each LF, a CR before it dropped; `delimiter` at each run of its UTF-8 bytes. Every cut is made on bytes, and each piece is stored as exactly the bytes it held. There is no cut by regular expression.
  - `maxFileSize`, a file source's cap on a batch file: a larger one is failed whole with the code `BATCH_FILE_TOO_LARGE`.
  - `onIncomplete` and `holdFor`: with `split: hl7`, a batch lacking its `BTS` or `FTS` trailer, or whose `BTS-1` or `FTS-1` count does not match, is held claimed for `holdFor` (5 minutes) by default and then failed with `BATCH_INCOMPLETE`, or stored as it is (`accept`), or failed at once (`fail`). An HTTP source answers 422 by default, or takes `accept`.
  - The `Idempotency-Key` request header on an HTTP source with `batch:`: with the body's hash, the origin of every piece's key, so a retry stores no piece twice. A key used before for another body answers 422 with `BATCH_KEY_REUSED` and stores nothing, and requests under one key are stored one after another, so two sent at once store their pieces once. Without the header the body's hash takes its place. The answer is 202 with `{"ids": [...]}`, every piece's id, never content.
  - `ctx.source.batch`, `{ piece, hash }`, for a message cut from a file or body: its place, and the first 16 hexadecimal digits of the SHA-256 of the whole, with the `BatchFacts` type.
  - A `batch` audit action, each batch's counts (`pieces`, `stored`, `failed`, `duplicates`) and, for one failed whole, its `reason`; and on `MessageSink`, the optional `receivePiece`, `batchDone` and `heldOrigin` the built-in sources call, with the `ReceivedPiece` and `BatchResult` types; on `MessageStore`, the optional `heldIdempotencyKey` that `heldOrigin` reads.
  - `pathways test` cuts each input of a channel with `batch:` the same way and compares all its pieces' outputs.

  A file source reads a batch file twice, a chunk at a time (once for its size, hash and envelope, once to store its pieces), so memory holds about one piece. Each piece is stored under the key of the claimed name, the file's hash and its place, and the file is deleted only once its last piece is stored: a stop part way leaves it claimed, and the next pass hands every piece in again with `resumed`, storing each once. A piece `@cosyte/hl7` cannot read is stored as failed with `batch: <code>` and no content while the rest go on; a file with no piece is failed whole with `BATCH_EMPTY`. A file failed whole is stored as one failed message and moved into `errorDir`, or into `.claimed/<channel>/failed/`, and no pass reads it again.

  On a channel with `storage.content: none`, a batch passes one piece at a time, and the pieces before one that fails were already sent and are not undone. A piece refused for good (its transform throws, or a destination rejects it) stops the batch: an HTTP source answers 422 with its code, and a file source moves the file into `errorDir`, or into `.claimed/<channel>/failed/` when `errorDir` cannot take it, so no pass reads it again and no piece is sent twice. A failure that may pass answers 503 with `Retry-After`, or leaves the file claimed, and the whole batch is sent again.

  The `hl7` cut uses `readMessages` from `@cosyte/hl7`, which the range the package already depends on, `^0.1.13`, includes: the dependency does not change.

  Nothing a caller must change: without `batch:` a source reads each file or body as one message, as before. A custom `MessageSink` needs none of the new methods; a batch read through one without `receivePiece` counts no duplicates, and one without `heldOrigin` stores a changed body sent under a used key as a batch of its own rather than answering 422. A custom store without `heldIdempotencyKey` does the same.

- fbc2b57: One channel can hand a message to another channel of the same project, through the store, with a channel destination or `ctx.route` in a transform.

  - New channel destination, `channel: { name, carryMeta }`: each output becomes a new message of channel `name`, stored in the same transaction as the delivery's record. `carryMeta` lists the `ctx.meta` keys copied to the new message, by name; none by default, and never all of them.
  - New channel source, `channel: {}`, with `routed` (only `ctx.route` feeds it), `maxPending` (10000 by default) and `maxHops` (8 by default). Nothing listens or polls; a paused or stopped channel still takes hand-offs as stored messages.
  - New `ctx.route(name, message)` in a transform: returns nothing, and the hand-off is stored in the same transaction as the transform's outcome, so it is kept only when the transform succeeds. A name that is no channel with a `channel:` source fails the message with `ERR_PATHWAYS_UNKNOWN_ROUTE`.
  - Start refuses a channel destination naming no such channel, a `channel:` source nothing names (unless it sets `routed: true`), and a loop of channel destinations, naming it (`a -> b -> a`).
  - Each handed-over message counts its hops; a hand-off past the target's `maxHops` fails with `ERR_PATHWAYS_HOP_LIMIT`, which catches a loop made through `ctx.route`. A hand-off that would leave its target holding more than `maxPending` messages waiting, counting what it brings, waits and tries again (`ERR_PATHWAYS_TARGET_FULL`), without counting an attempt; a store without `handOff` counts the same way. A transform that routes more messages to one target in one run than that target's `maxPending` fails its message with the new `TOO_MANY_ROUTES_CODE`, `ERR_PATHWAYS_TOO_MANY_ROUTES`, since waiting could never let it through.
  - A hand-off to a channel whose format is `hl7v2` takes one message, as a source's message does when it enters the engine: a body holding a second message header is refused before the target stores it, with `MULTIPLE_MESSAGES`. The channel destination's delivery fails (`hand-off: MULTIPLE_MESSAGES`), or the message whose transform routed it does, and nothing is handed over.
  - Each handed-over message names its parent: the source channel, message, delivery (none for `ctx.route`) and the parent's generation, above 0 for a replay or resend. `pathways messages show` prints the parent and the messages handed over; `pathways status` prints `feeds:` and `fed by:`; the retention archive keeps the link.
  - New optional store methods `handOff` and `children`, and the types `HandOff`, `HandOffFrom`, `HandOffResult` and `MessageParent`. A custom store without `handOff` still works: the engine stores each hand-off with `receive` under an idempotency key built from the source channel, the delivery or message, and the generation, then records the source, so a crash between the two hands over once. `carryMeta` reads the message's metadata through the store's optional `messageMeta` (JSON text, through the codec); a store without it carries nothing.
  - New expand schema step `0015-channel-links`, numbered after `0014-idempotency-claims`: five nullable columns on `messages` and an index, applied at start. A handed-over message claims its idempotency key on the target channel (`idempotency_claim`), as a received one does, whether it is stored by `handOff` or through `receive`.
  - `pathways replay` refuses, changing nothing, a message whose transform calls `ctx.route` (reason `routes`); `pathways replay --resend` works.
  - What a caller must change: a custom store whose `listMessages` or `message` results are compared whole may now see `parent` and `hops` on a handed-over message; a test that compares a transform's `ctx` whole now sees `route`. Nothing else.

- fbc2b57: A channel's transform module may export `onStart` and `onStop`, each message gets one `settled` event, and `pathways start` records its starts and stops in the audit log.

  - New: `export const onStart: OnStart` and `export const onStop: OnStop` beside a transform's default export. `onStart(ctx)` runs in the channel's worker before it takes a message, on every new worker (at start, on a reload, under `pathways test`, `replay` and `verify`, and in the worker that replaces one after a timeout, a memory cap or a crash), so it must be idempotent. `ctx` holds `channel`, `config` and a `logger` that takes a code and numbers only. `onStop()` runs before a worker ends on a clean stop (`SIGTERM` and `SIGINT` among the ways, and a reload) and is cut at its limit. Both have a new setting, `scriptTimeout`, the transform `timeout` unless set. These scripts are user code with the worker's full Node.js access, not a sandbox.
  - An `onStart` that throws or runs past its limit is a load failure: the start stops, or a reload is refused. In a replacement worker, that channel stops, the health endpoint answers 503 with `transform: { loaded: false, kind, name, code }` for it, and the other channels run on until `pathways channel reload` loads it. Before, a transform that would not load in a replacement worker ended the whole run.
  - New lifecycle event `settled` (`SettledEvent`), once per message when its last delivery is delivered or failed for good, or it was filtered, or its transform failed, with the message id and each destination's `{ index, name, state }`. It is recorded on the message's row by one conditional update, so a restart sends one the last run did not record and nothing is sent twice; a replay or a resend settles again. `LIFECYCLE_EVENTS` gains `settled`: a hook that switches on every event adds a case for it.
  - Schema step `0016-settled` (numbered after `0013-destination-keys`, `0014-idempotency-claims` and `0015-channel-links`, which came first) adds `messages.settled_generation` (expand only) and marks every message that had already ended as settled, so none of them gets an event. It also adds the index `messages_by_channel_settled`. A custom store (`storage.module`) may implement the new optional `settle`, `unsettled` and `requeuedUnsettled`; one without the first two runs as before and sends no settled events, and one without `requeuedUnsettled` sends a replay's settled event at the next start when the replay filtered the message or failed again.
  - `AuditAction`, `AUDIT_ACTIONS` and `AuditEventAction` gain `engine-start`, `engine-stop` (each with `version`, `channels` and `node`) and `unclean-shutdown` (written at a start when the run before left no `engine-stop` of its own node; a stop is matched to its start by node id). A hook or tool that switches on every audit action adds cases for them. A hook on `engine-start` is how a project runs a step once a deployment is up; there is no project-wide deploy script.
  - Hooks stay best effort: past 1,000 waiting events for one hook new ones are dropped, and the audit log and the message states are what to count from where every one matters.
  - A known cost of recording settlement: `pathways start --once` on 100 HL7 v2 messages read slower in each of six benchmark runs on GitHub-hosted runners, by +3.2% to +4.8% (medians +3.2%, +4.3%, +4.7%, +4.6%, +4.3% and +4.8%; intervals from +3% to +7.1% across the six), and on 1 MiB of JSON by +0.5% to +2.3% (intervals 0% to +2.9%). Each message now pays one settle update, and each start a sweep for unsettled messages and its audit entries.

- 63e2bbf: A transform and a filter per destination.

  - A destination block takes three new keys: `transform:`, its own transform module; `name:`, unique in the channel (lowercase letters, digits and hyphens); and `format:`, the format the destination sends, the channel's by default. A destination's `format` sets the extension a file destination writes and the `Content-Type` an HTTP destination sends.
  - A destination's transform runs in the channel's worker, in the same pass as the channel's transform and under its one timeout and memory cap: once for each channel output, which it reads parsed in the channel's format, and what it returns is written in the destination's format. It returns a message, several, or `null` to filter that destination for that message. Its context is the channel transform's with `ctx.destination`: `{ index, name, kind }`, typed by the new exported `DestinationFacts`. A destination transform that will not load stops the channel's start, and `TransformLoadError` names the destination in its new `destination` field.
  - A new delivery state, `filtered`: the destination's transform returned nothing, so nothing is sent to it. It is done, as a delivered one is, for a message's state, for dropping content after delivery and for retention. When every destination filters a message, the message is `filtered`. A throw in a destination's transform fails that destination's delivery only, with its error stored through the codec, encrypted under encryption, and never logged (a `destination-transform-failed` log event carries its kind, name, code and where); the other destinations go on.
  - On a channel that stores nothing (`storage: { content: none }`), each destination is sent what its own transform made; one whose transform throws is sent nothing, the others are still sent the message, and the sender is told not to send it again (`TRANSFORM_FAILED`), with `pass-transform-failed` naming the destination.
  - `pathways replay` runs the channel's and every destination's transform as they are now; `pathways replay --resend` sends each destination the bytes stored for it, even after its transform changed, and never another destination's: a destination added since the message's last transform is sent nothing, and the command and the `resend` audit entry count it (`not-stored`, `notStored`). `pathways verify` runs the destination transforms and compares each destination with the outputs stored for it, or with its own sample file, named as `pathways test` names it; a destination with nothing stored is counted as `not-stored` and not compared.
  - Each delivery records the destination it was made for by its identity: its `name:`, or, without one, its kind and target (a folder, a URL, a host and port, a module), kept as a hash in a new `deliveries.destination_key` column (schema step `0013-destination-keys`, an expand step: a column that may be null and an index; numbered after `0012-nodes`). The engine's queue, a resend, `pathways verify` and `pathways messages show` find each destination's deliveries by it, never by the destination's place in `channel.yaml`'s list, so adding a destination anywhere, removing one or reordering them never sends, resends or compares one destination with another's outputs. That needs each destination's identity to be its own: `pathways validate` and a start refuse a channel with two destinations that have no `name:`, the same kind and the same target, naming both (`destinations.2: sends where destinations.0 sends, and neither has a name:`), and ask for a `name:` on each. At a channel's first delivery pass the engine holds the pending deliveries none of its destinations was made for, logged as `deliveries-held` with a count: one made for a destination the channel no longer has (`destination-gone`) stays pending, and is sent if it comes back; one queued before this release, which records no destination (`destination-unknown`), is marked failed with the error `delivery: destination-unknown`, so its message can be replayed. A resend of a message stored before this release is refused with the new `ActionRefusal` `destination-unknown`; a replay runs it again. Renaming a destination, setting a `name:` on one without, or changing the target of one without a name makes it a new destination: give each destination a `name:` when you add it. `pathways test` compares one expected file per destination on a channel with destination transforms, `<input>.expected.<destination name, or its place from 1>.<extension>`, and a missing file expects that destination to filter the input out. `pathways messages show` lists a filtered delivery and each destination's name; `pathways status` counts filtered deliveries.

  The public API additions: the `transform`, `name` and `format` keys and the `DestinationConfig` fields of the same names; `DeliveryStatus` gains `filtered`, and `DeliveryCounts` and `DeliveryTally` an optional `filtered` count; `DestinationFacts` and `TransformContext.destination`; and a store change, with the new `DestinationOutcome` and `TransformOutputs` types. A storage adapter's `completeTransform` may now be given `{ byDestination }`, one `DestinationOutcome` per destination, in place of the list of outputs; a `RequeueRequest` may carry `byDestination` in place of `outputs` for every destination, where a resend gives a destination with nothing stored `{ notStored: true }`, which writes no delivery, and `RequeueResult` and `ReplayResult` gain an optional `notStored` count; and `outputs(messageId, destination?)` takes the destination to read, by its place or, as the new `DestinationKey` `{ key }`, by its key. `completeTransform` takes a fifth argument, `keys`, each destination's key in order, and `RequeueRequest` a `keys` field: storage records each on its deliveries, and the built-in `Store` refuses `{ byDestination }` without them. `NextDeliveryOptions` gains `key`, so the engine claims the deliveries made for a destination wherever it stands; `StoredDelivery` gains `destinationKey`; and `MessageStore` gains the optional `holdDeliveries`, returning the new `HeldDeliveries` counts. A destination with no output is written as one delivery with `seq` -1, `filtered`, or `failed` with its error. What a caller must change: a channel with two unnamed destinations of one kind and target, such as one `module` destination listed twice with different `options`, gives each a `name:`; and a project with its own storage adapter handles the store change. A storage adapter handles the changes above, as the built-in `Store` does; one that ignores `keys` and `key` still runs, finding deliveries by place as before, but a resend through it is refused as `destination-unknown`, since its deliveries record no destination. Before upgrading a project whose database has pending deliveries, let them deliver, or replay their messages after the upgrade.

- c6503dd: An `hl7v2` message a transform returns is now written in the character set its MSH-18 declares, so
  a Latin-1 message that nothing changed leaves byte for byte as it arrived. Check this before you
  upgrade if a sender leaves MSH-18 blank and sends non-ASCII bytes (Latin-1, say): a channel whose
  transform edits any field in a segment that holds such a byte, even with ASCII text, now fails that
  message's output with `UNENCODABLE_CHARACTER`, where it used to send it re-encoded as UTF-8. Have the
  sender declare MSH-18, or set the channel's new `hl7v2: { assumeCharset: "8859/1" }` block, which
  reads and writes a message whose MSH-18 is blank in that set. Setting MSH-18 inside the transform
  does not help: such a message holds its bytes as they arrived, and they cannot be moved to another
  set. The same holds for a message whose MSH-18 names a set the reader does not decode.

  Before, every `Hl7Message` was written as UTF-8. A message that holds a character its set has no
  byte for now fails its output with `UNENCODABLE_CHARACTER`, an error that names the segment, field
  and set but never the field's text; for a blank MSH-18 it also names `hl7v2.assumeCharset`. A
  transform that wants UTF-8 out of a message that declares a set such as `8859/1` sets MSH-18 to
  `UNICODE UTF-8`; returning `message.toString()` sends UTF-8 as before. The `@cosyte/hl7` dependency
  is raised to 0.1.13, the first release with `toBytes()`. `Hl7v2Settings` is exported as a type.

- fbc2b57: The HTTP destination takes a method, fills its URL from each message's metadata, names each output with an idempotency header, and checks every address it connects to.

  - `method:` sends each output by `POST` (the default), `PUT`, `PATCH`, `DELETE` or `GET`; `GET` and `DELETE` send no body and no `Content-Type`, so a destination with either and `ack: xml` is refused when the configuration loads: there is no message for the acknowledgement to answer.
  - The `url:` path, and each value of the new `query:` mapping, may hold placeholders, a `ctx.meta` key in braces such as `{mrn}`. Each is filled per message, percent-encoded, so a value never changes the scheme, the host or the port; a placeholder anywhere else is refused when the configuration loads. A key the metadata lacks, an empty path value, a value of `.` or `..`, or text that cannot be encoded fails that delivery for good, with an error naming the key and never the value (`rejected: URL_TEMPLATE_MISSING mrn`). `ctx.meta` is still empty in this release, so a URL with a placeholder fails every delivery until it can be set. The docs warn that values in a URL reach server and proxy logs.
  - `idempotencyHeader:` names a header sent on every attempt, its value `<messageId>-<seq>`.
  - Every connection an HTTP destination opens is checked at connect against the address it connects to, so a name that rebinds to an internal address is caught too: loopback, link-local (cloud metadata), private and unspecified addresses are refused, and the delivery retried with the code `ADDRESS_REFUSED`, unless the new `allowNetworks:` list names the network.
  - What a caller must change: an HTTP destination whose host is, or resolves to, a loopback, link-local or private address (`127.0.0.1`, `10.x`, `192.168.x` and the like) now needs `allowNetworks:` naming it, such as `allowNetworks: [10.20.0.0/16]`; until then its deliveries wait with `ADDRESS_REFUSED`. The webhook hook is not checked.
  - API additions: the channel keys `method`, `query`, `idempotencyHeader` and `allowNetworks` on an HTTP destination; `OutgoingMessage` gains an optional `meta`, handed to a destination that fills its URL from it; `MessageStore` gains the optional `messageMeta`, which reads one message's metadata back through the codec (a custom store without it hands over none). No custom connector or store needs to change.

- 68e19cb: An HTTP destination can settle each delivery by an HL7 v2 XML acknowledgement.

  - A new key on an `http` destination, `ack: xml`: a 2xx answer's body is read, up to 1 MiB and within the destination's `timeout`, as an HL7 v2 XML acknowledgement, the answer a web service that takes v2 XML sends on the same connection. Its `MSA.1` settles the delivery: `AA` or `CA` is delivered; `AE` or `CE` is retried, coded `ACK_AE` or `ACK_CE`, within the destination's retry settings; `AR` or `CR` fails the delivery for good. That is the other way round from an MLLP destination, following the public description of the exchange this was written for. A status that is not 2xx is read by the status table as before.
  - An answer is read in one shape only: exactly one `MSA` in the whole document, a child of its root; exactly one `MSA.1` and at most one `MSA.2`, children of that `MSA`, holding text alone; at most one `MSH`; and a code that is exactly `AA`, `AE`, `AR`, `CA`, `CE` or `CR`, with no whitespace and in upper case. An answer in any other shape, not XML, over 1 MiB or cut short is retried as `ACK_UNREADABLE`, never settled by the first `MSA` or `MSA.1` found.
  - The message sent is read once per delivery, before its first POST, whatever its size. It must hold exactly one `MSH`, at any depth, with exactly one `MSH.10` holding text alone; an acknowledgement whose `MSA.2` is not that `MSH.10` is retried as `ACK_CONTROL_ID_MISMATCH`. A message sent as XML of another shape (no `MSH`, a batch with several, or an `MSH` without one `MSH.10`) is not sent, and the delivery fails at once with the reason `SENT_XML_NO_CONTROL_ID`, since the same body goes on every attempt and a retry could only post it again. A message sent as XML the reader refuses (not well-formed, not UTF-8, or with a document type declaration or an entity anywhere) is not sent either, and fails at once with the reason `SENT_XML_UNREADABLE`. The control ID check is skipped only for a body that is not XML at all, so a pipe-delimited body sent with `ack: xml` is settled by its code alone.
  - `ack: xml` needs the destination's format to be `hl7v2` or `text`; with `fhir`, `x12`, `ccda`, `json` or `csv` the channel is refused at load.
  - The XML is read with `@cosyte/ccda`'s hardened reader: no document type declaration or entity, at most 32 elements deep and 20,000 nodes. Elements are matched by local name, so the HL7 namespace, a prefix and no namespace read the same. Only `MSA.1`, `MSA.2` and the sent message's `MSH.10` are read; nothing of the answer is logged.

- 34939d3: One message per idempotency key, even when it is handed in twice at the same moment.

  Two hand-ins of one message under one idempotency key at the same moment, on two connections or two nodes, could both be stored on PostgreSQL, MySQL and MariaDB: each inserted its row and then looked the key up, and neither saw the other's row before it committed. (On SQL Server the second lookup already waited for the first row, at its default locking read committed.) Now each message claims its key in the same statement that inserts it, in a new `messages.idempotency_claim` column that a unique index covers (`messages_by_channel_idempotency_claim`, schema step `0014-idempotency-claims`, an expand step numbered after `0013-destination-keys`). The second insert waits for the first's transaction and yields to its row, so a resumed hand-in gets that message's id back with `alreadyStored` and nothing new is stored. This holds on SQLite, PostgreSQL, MySQL, MariaDB and SQL Server, each at its default isolation level. A hand-in that is not resumed is still always stored, without the claim when another message holds it. A resumed hand-in whose claim is free still looks for an earlier message under its key, so it finds one stored before this release, or by an older Pathways beside it.

  The schema step gives each key's claim to the earliest message of its channel stored under it. A database that already holds two messages of a channel under one key keeps both, each with its body, status and deliveries; only the earliest holds the claim, and a resumed hand-in finds that one, as before. To roll the step back, stop every engine and drop the index and the column.

  An id a server spent on an insert that yielded is not used again, so message ids can skip a number after a hand-in that found its message stored. A retention archive now carries `idempotencyClaim` with each message; an archive written before this release has none and still opens. `StoredMessageRow` gains `idempotencyClaim`: a store wrapper that builds those rows itself sets it, `null` when it keeps no claims. Nothing else a caller must change. A custom `MessageStore` that more than one connection writes to should make its key lookup and insert one atomic step, as the `MessageStore.receive` documentation now says.

- 8e0edd5: An `xml` format: a channel with `format: xml` hands its transform any XML body as a parsed DOM document, an `XmlDocument`.

It refuses a DTD or an entity declaration (`XXE_OR_DTD_PRESENT`), any entity reference other than the five XML predefines (`ENTITY_EXPANSION_LIMIT`), a body that is not well-formed (`NOT_WELL_FORMED_XML`, which also covers text outside the root element and a character XML 1.0 forbids, as it is or as a character reference) and one that is not valid UTF-8 (`ERR_ENCODING_INVALID_ENCODED_DATA`). A changed or new document is written as UTF-8, its XML declaration naming `UTF-8`, then read back under the channel's `xml:` caps and compared with the document node by node; one that does not read back the same fails its output with `XML_NOT_WRITABLE`, as does a comment holding `--` or ending in `-`, a processing instruction holding `?>` or named `xml` other than the declaration, and a character XML forbids. A new element in a default namespace is made with `createElementNS`: one made with `createElement` has no namespace and is refused. A document is written this way whatever the channel's format, so a transform can turn another format into XML.

- 608eb3a: `pathways replay --status failed` replays every failed message in a scope, counted first and resumable.

- d057771: An MLLP source can dial out to its sender, and can send each ACK to another address.

  - New `source.mllp` key `connect: { host, port }`, in place of `port`: the source dials out to the sender and reads messages from that connection, storing each and answering it on the same connection. A dial that fails, or a connection that drops, is dialled again after 1 second, doubling to 5 minutes and back to 1 second once a connection opens; until then the health report shows the source `down`, and the engine logs `source-lost` with a code such as `ECONNREFUSED`, `CONNECT_TIMEOUT` or `MLLP_CONNECTION_CLOSED`. With `connect`, the `tls` block is a client's: `tls: {}` verifies the sender against Node.js's built-in roots, `ca` trusts your own CA, and `cert` and `key` (or `pfx`) present a client certificate. `port`, `host`, `maxConnections`, `keepOpen` and `replyTo` cannot be set with it. The engine logs the new event `mllp-connected` at each connection. A stop closes the dialled connection once the message it is handling has been stored and answered, cut off at `drain.timeout`.
  - New `source.mllp` key `replyTo: { host, port }`: each ACK goes on a new connection to that address, never on the connection the message came on, and the address comes from the channel's file only, never from the message. Over TLS the reply host is verified against the source's `tls.ca`, or the built-in roots. A reply that cannot be sent leaves the message stored and logs the new event `mllp-reply-failed` with the message id and a code: `SEND_TIMEOUT` when the reply host takes the connection but the ACK cannot be written out within `connectTimeout`.
  - New `source.mllp` key `connectTimeout` (a duration, 10 seconds by default) bounds each connection the source opens itself, its TLS handshake included. It is refused on a source with neither `connect` nor `replyTo`.
  - An MLLP source's `port` is required only when `connect` is not set, in `pathways start` and in the JSON Schema `schema/channel.json` an editor reads. A configuration that loaded before loads unchanged, and nothing a caller writes needs to change.
  - The MLLP page now says that over TLS a sender that stalls its handshake holds a `maxConnections` place until Node.js's 120 second handshake timeout, and how to shorten it.

- 3d37055: An MLLP source can bound its connections and messages, and both MLLP ends choose their TLS version and cipher suites by a named profile.

  - New `source.mllp` keys: `maxConnections` (1 to 100,000), `receiveTimeout` (a duration), `maxMessageSize` (a size such as `4MB`) and `keepOpen` (a boolean). A connection over `maxConnections` is closed at accept, before any byte is read or any TLS handshake starts; the engine logs the new event `mllp-connection-refused` with the cap and the code `MLLP_CONNECTION_LIMIT_REACHED`, never who connected. `receiveTimeout` closes a connection that goes that long without a whole message, an idle one and one that sent part of a message and stopped; it is off by default. A frame over `maxMessageSize` closes the connection and nothing of it is stored. `keepOpen: false` closes each connection once every message it brought has been stored and answered, its ACKs written out first.
  - New keys in an MLLP source's or destination's `tls` block: `minVersion` (`TLSv1.2`, the default, or `TLSv1.3`), `profile` (`bcp195`, the default, or `atna`), `ciphers` (an OpenSSL cipher list, refused together with `profile`), and `pfx` with `passphrase` (a PKCS#12 file in place of `cert` and `key`, its passphrase read at start from a secret reference). A pfx that does not open, or a cipher list OpenSSL takes nothing from, stops the start naming the key, never a path or the passphrase.
  - The health body gains `connections: { refused }` on each channel whose source is MLLP: how many connections that source closed at accept since the engine started. Other channels are unchanged.
  - Three changes in behaviour. An MLLP source now holds at most 100 connections at once where it had no cap, and takes messages up to 4 MB where `@cosyte/mllp` allowed 16 MB; set `maxConnections` or `maxMessageSize` to keep more. Both MLLP ends now offer only the `bcp195` cipher suites (TLS 1.3's, and for TLS 1.2 ECDHE with AES-GCM) where they offered Node.js's default list, so a TLS 1.2 peer that can use none of them now fails the handshake; set `profile: atna` or a `ciphers` list for it.
  - `@cosyte/mllp` moves to `^0.1.12`, which brings the connection cap, the client connect timeout and PKCS#12 support these keys use.

- 13a87cc: MySQL and MariaDB storage binds every value on the server.

  - Before, the mysql2 driver escaped each statement's values and wrote them into the SQL text. Under a server `sql_mode` with `NO_BACKSLASH_ESCAPES` that escaping was wrong: a backslash in a value (common in HL7 v2) was stored doubled, and a quote ended the string, so the rest of the value could run as SQL. Now every statement that carries a value runs as a prepared statement the server binds, so values are stored byte for byte under any `sql_mode`. PostgreSQL, SQL Server and SQLite already bound values apart from the text.
  - Each MySQL or MariaDB connection keeps its 128 most recently used prepared statements. What an operator must change: nothing at the default `pool.max` of 10. The server's `max_prepared_stmt_count` (16,382 by default) caps prepared statements across all its connections, so where several engines, standbys or a large `pool.max` share one server, raise it to at least 128 times the connections Pathways opens to it, plus what other applications there prepare. A statement over the cap fails with error 1461 (`ER_MAX_PREPARED_STMT_COUNT_REACHED`).

- 607845e: Each engine is a node with an id, a row in the database and a heartbeat, so `pathways nodes`, a refused start and the health body say which engines run, which version, and whether each is alive.

  - The node id is `node.id` in `pathways.yaml` (1 to 64 letters, digits, dots, hyphens and underscores; `{ env: NAME }` works), or one generated at the first start and kept in the project's `.pathways/node-id`, so a restart is the same node. The engine lease is taken under it, and the health body's `node` is it. Before, each process drew a fresh id.
  - New schema step `0012-nodes` (expand) adds a `nodes` table: node id, host, process id, start time, Pathways version, schema generation, role (`single`, `standby`, `active`, `proving`, `draining` or `fenced`), a draining flag, the stale bound and the last heartbeat. It holds no message content and no URL. Every time in it comes from the database's clock.

A clean stop removes the row. A node shows stale once its last heartbeat is older than three intervals (15 seconds by default).

New log events: `node-id-unsaved`, `heartbeat-failed`, `node-rejoined`, `node-duplicate` and `node-leave-failed`.
  - A custom store may implement the five optional `MessageStore` methods `joinNode`, `nodeHeartbeat`, `leaveNode`, `nodes` and `forgetNode` (types `NodeInfo`, `NodeRow`, `NodeJoin`, `NodeReplace`, `NodeSelf`, `NodeState`, `NodeRole`, `NodeStore` and `NODE_ROLES` are exported). A store without them needs no change: its engines write no node row. Two engines run from one project folder on one host now share the kept id, so the second is refused as a duplicate node; give each its own `node.id`.

- 3eb4b70: A file source and a file destination can read and write objects in an Amazon S3 bucket or an Azure Blob Storage container.

  - New channel keys: `source.file.s3` and `destinations[].file.s3`, each `{ bucket, region, endpoint, plaintext, pathStyle, timeout, singleNode, mode }`, and `source.file.azblob` and `destinations[].file.azblob`, each `{ account, container, endpoint, connectionString, plaintext, singleNode, mode }`. With either, `dir` is the key prefix in the bucket or container. Nothing changes for a channel without them.

The source reads the object's size with a `HEAD` before the claim (for `maxSize`), lists the prefix a page at a time, reads and deletes the object with `If-Match` on its entity tag, stores it under a key of its bucket, key, tag and modification time, and finishes its own channel's markers on the next pass, so a stop at any step stores nothing twice.
  - At its first pass the source checks with a probe that the store honours `If-None-Match`, and refuses one that does not (`ERR_PATHWAYS_OBJECT_NO_CONDITIONAL_WRITE`) unless the source says `singleNode: true`: then it claims nothing and deletes each object once stored, which is safe only while one engine reads the prefix.   - The destination writes each output as one object with `If-None-Match: *` (`mode: create`, the default): an object of the same bytes there counts as delivered, and one of other bytes rejects the message with `OBJECT_EXISTS`. `mode: overwrite` replaces it.
  - S3 credentials come from the AWS SDK's default chain, and Azure's identity from its default chain (a managed identity, a workload identity, or the environment), or a connection string read from a secret reference. An `http://` endpoint, or a connection string that names one, needs `plaintext: true`.
  - They run on `@aws-sdk/client-s3`, and on `@azure/storage-blob` with `@azure/identity`, optional peer dependencies a project installs to use them; the Docker image carries them.
  - `keepProcessed`, `doneFile`, `errorDir` and `readTries` are refused with an object store.
  - New docs pages "Read and write Amazon S3" and "Read and write Azure Blob Storage"; the configuration reference and the codes page list the new keys and codes.

- 90f31f9: Retention gains separate clocks, content-only pruning and sealed archives written and checked before anything is deleted. `retention: 30d` and the 30-day default run exactly as before.

  - `retention:` may be written out as `{ content, metadata, failed }`, in `defaults:` or a channel. `content` empties a done message's bodies, error texts and `ctx.meta` once it is that old and keeps its row; `metadata` deletes the row (30 days when unset); `failed` deletes a failed message (kept until replayed or cleared when unset). A written-out block also deletes, on the metadata clock, a message whose content was dropped; the shorthand still leaves it. Any block counts as written out, so adding only `archive` or `audit` to `retention:` switches this on: keep the shorthand, or set `metadata:` as long as those rows should stay. `metadata` shorter than `content` is refused when the project loads. `pathways replay` refuses a message whose content went with `content-dropped`, as for `dropAfterDelivery`.
  - `retention.archive: { dir }` in `pathways.yaml` writes every batch retention is about to change to a sealed archive first, every column of each message's row and of each of its deliveries, every generation: its `ctx.meta`, error texts and every body among them. Gzipped NDJSON with a header (format version, channel, key id, created, step) and a trailer (count and an HMAC-SHA-256 over the records), encrypted with the envelope stored messages use, one data key per file. Each is written to a `.partial` file, flushed, renamed, its folder flushed, read back and checked, and recorded as a new `archive` audit action, and only then are its messages changed, in batches of at most 500. A crash leaves a duplicate archive, never a loss. When an archive cannot be written, checked or audited, that channel is left alone for the run and the engine logs `retention-skipped` with the channel and code; `pathways retention` prints it and exits 1. `archive` with `encryption: none` is refused at load.
  - `retention.audit` takes `never` alone, the default: the audit log is never pruned.
  - `pathways retention --dry-run` prints each clock's counts.
  - New in the API: the optional `MessageStore` methods `countExpiring`, `listExpiring`, `applyExpiry` and `archiveRows` (the `RetentionStore` type), with `RetentionQuery`, `RetentionStep`, `MessageRows`, `StoredMessageRow` and `StoredDeliveryRow`; the archive record types `ArchiveHeader`, `ArchivedMessage`, `ArchivedDelivery` and `ArchiveErrorCode`; `archive` in `AuditAction` and `AuditEventAction`. A custom store needs no change unless a project sets the content or failed clock or an archive: then it implements the four methods, and without them retention leaves its channels alone with `ERR_PATHWAYS_RETENTION_UNSUPPORTED`. Code that switches over `AuditAction` or `AuditEventAction` gains one case to handle.

- d2faab1: A channel can send each output as an email, through a new `smtp` destination.

When some recipients are refused and others taken, the delivery is rejected (`SMTP_RCPT_PARTIAL`) so an operator sees it, unless the block sets `onPartialRefusal: delivered`; either way the recipients taken have the email, and `smtp-recipients-refused` logs the count and the outcome, never an address. - 2adffa2: Control one channel of a running engine: `pathways channel pause`, `resume`, `stop`, `halt` and `reload`, without restarting the others.

  - New command `pathways channel <pause|resume|stop|halt|reload> <name>`, with `--deadline` for `stop` and `halt` and `--json`. `pause` stops the source taking messages in while stored messages go on to delivery; `stop` also ends the channel's work after the message in hand, waits up to the deadline (30s by default) and reports what it left; `halt` cuts the delivery in flight off at once, leaving it pending to be sent again, flagged, after a `resume`; `reload` loads the channel's transform, its settings and the transform's `config:` blocks in a fresh worker and swaps them in between messages. A reload is refused, keeping the running transform, when the configuration is invalid or a `config:` value names an environment variable that is not set, the new transform throws as it loads, the channel is gone, a stop is still draining it, or the change is to the source, destinations, format or hooks (named, as needing an engine restart). Two reloads run one after the other, and a reload a stop overtakes (queued, or while its transform loads) is refused too. Two commands at once leave the source as the last one set: one that pauses or stops the channel while a resume is opening its source closes it again before it takes a message in. `--deadline` is at most 24 days, the longest wait a timer holds; a longer one is refused.
  - `pathways start` listens on a control socket: a Unix socket named by a hash of the project path in a `pathways-<uid>` folder it makes with mode 0700 (under `XDG_RUNTIME_DIR`, the temporary folder, or `/tmp`, within the socket path limit), or a named pipe on Windows. A stale socket is removed; a start that finds another engine answering there refuses and exits 1. One line of JSON each way, with a version, a 4 KB request limit and a 5s idle limit; replies carry states and counts, never content. `pathways channel` says `engine not running` when nothing answers.
  - Paused and stopped channels are kept in a new `channel_states` table (migration `0009-channel-states`, an expand step, a new table only, on SQLite and the four servers), read at the top of each pass by every engine on the database: a restart keeps a channel paused, and a command given to one engine reaches the others within one pass. Dropping the table with every engine stopped sets every channel running. The engine changes the channel before it stores the state, so a stop takes hold at the next message; a state the database does not store is put back, and the command is refused as `state-not-stored`.
  - Each command is written to the audit log as `channel-pause`, `channel-resume`, `channel-stop`, `channel-halt` or `channel-reload`, with the user the command reports, a refused one too (a channel the engine does not run among them); the socket folder, open to that user alone, is the trust boundary. On Windows the pipe's name can be guessed by another local user, a weaker boundary the how-to describes.
  - The health body gains each channel's `state` (`running`, `paused` or `stopped`); neither paused nor stopped changes the answer from 200.
  - API additions: `MessageStore` gains the optional `channelStates` and `setChannelState` (a custom store without them keeps a channel's state in the engine only, and a restart forgets it); `OutgoingMessage` gains an optional `signal`, aborted on a halt, which a custom destination may pass to its client; new exports `ChannelRunState` and `ChannelStateStore`. `AuditAction` gains the five channel actions. No caller needs to change.
  - New log events: `channel-state`, `channel-states-unread`, `channel-state-unstored`, `channel-reloaded` and `delivery-halted`.

- 71bc365: JSON Schemas for `pathways.yaml` and `channel.yaml`, and a `pathways validate` command.

- 20b996c: A schedule per polled source, a deadline on each pass and on every delivery, and a way for a running source to say it lost its connection.

  - A `file` or `module` source may set `poll:` beside its kind: an interval such as `30s`, `onStart` for one pass at start, or a mapping with exactly one of `every`, `cron` (five fields, read with `timezone`, `UTC` by default) or `onStart: true`, and a `deadline` (`5m` by default). Without it, a source is polled every `pollInterval`, as before. `poll` on an `http` or `mllp` source, `timezone` without `cron`, a cron expression that is not five fields, or a time zone Node does not know is refused, naming the file and key. Cron expressions are read by croner, a new dependency (MIT, no dependencies of its own).
  - Each source's pass runs beside the engine loop, so a source that hangs holds up no other channel. A pass never overlaps itself: one that comes due while the last `poll` call has not returned is skipped and logged as `poll-overlap`. A pass past its deadline is cut off and logged as `poll-deadline`: the signal handed to `poll` aborts, and each later `sink.receive` of that pass rejects with the code `POLL_DEADLINE` before it stores anything, so the source keeps the message. A pass missed while the engine was down, or while the last one ran, is not made up. When `pathways start` stops, a pass under way finishes storing what it is storing and takes nothing more in, its `poll` call is waited for up to its deadline, and what the sources took in goes on through the transform and delivery before it exits, as before. A `poll` that rejects once its pass is cut off, such as one that handed the signal to its client and got an `AbortError`, is part of the cut and not an error; one that rejects before still ends the run with its error. `pathways start --once` polls every source once, whatever its `poll`.

At the deadline the destination's `signal` aborts and the attempt is retried as any other failure, with the code `DELIVERY_TIMEOUT`, not flagged as a possible duplicate, though the receiver may have the message already, so a receiver should drop duplicates by `messageId` and `seq`. A code that is not letters, digits and `_.:-` (at most 64) is kept as `UNSPECIFIED`, so no error text reaches a log. `SourceConnector.poll` takes an optional second argument, the pass's `signal`. Code written against these types keeps compiling unchanged.
  - Each output's `messageId` and `seq` stay the same on every attempt and resend; the delivery docs now say how a receiver can use the pair to drop a copy.

Equal values give equal tags, so the tags show which messages may share a value (one patient's messages all carry the same tag), while other values can share a tag too, about `d / 2^b` of them with `d` distinct values in the channel; a search reads each row with the tag, decrypts its metadata and keeps only the rows that hold the value. Values are compared exactly as stored text: case, surrounding spaces and Unicode form all count, so normalize a value before storing it. With `b` bits, a search reads about one row in 2^b of the channel's rows that it then drops: one in 4,096 at the default.
  - `pathways validate` and `pathways start` warn about an index on a key whose name says its values are few or guessable (sex, status, a birth date and the like), and still run it. An `index:` block under `encryption: none` is a configuration error.
  - `pathways messages --channel <name> --where key=value` (repeatable, every pair must hold) lists the matching messages with the other filters of `messages`. It searches under every master key id the provider holds, reads at most 10,000 rows a page, and writes a `search` audit entry with the keys and filters, never the value, before it reads any row; it does not search when the entry cannot be written. A key the channel does not index is a usage error.
  - `pathways rekey` re-encrypts each message's metadata under the current key and derives its tags again from it under the current key and the channels' `index:` blocks, so it also tags messages stored before an index was added. It prints how many messages it retagged when any.
  - Message metadata is stored encrypted, like the body. In this release nothing in the engine sets `ctx.meta` yet; metadata is stored when the code that stores a message passes it.
  - Schema step `0010-message-meta` (expand) adds a `meta` column to `messages` that may be null, and a `meta_index` table. It only adds, and has no rollback step. Retention deletes a message's tags with it, and `storage.content: dropAfterDelivery` clears a message's metadata and deletes its tags when it drops the content, so such a message can no longer be found by metadata.
  - New in the API: `MessageMeta`, `MetaTag`, `MetaCondition`, `MetaCandidate`, `MetaCandidateQuery`, `StoredMeta` and `MetaStore`; the optional `meta`, `storedMeta` and `metaTags` on `StoreReceiveOptions`; the optional `ids` on `MessageQuery`; the optional `MessageStore.metaCandidates`; the optional `keyIds` and `deriveIndexKey` on `KeyProvider`; and `retagged` on `RekeyCounts`. A custom store needs no change: without `metaCandidates` it cannot be searched by metadata. A custom key provider needs no change unless a channel has an `index:` block: then it implements `deriveIndexKey`, and `pathways start` refuses the block on a provider without it.

- 3691d71: Liveness and readiness probes a load balancer or an orchestrator can ask without a token, and a health body that says which engine answered.

  - New `probes` block in `pathways.yaml` (`port`, `host` defaulting to `127.0.0.1`, and `plaintext: true`, which it requires), off unless set. It opens a second listener, plain HTTP with no token, that answers `GET /livez` and `GET /readyz` with 200 or 503 and one word, and nothing else: no channel name, no count, nothing stored.
  - `/livez` is 503 `stalled` only when the engine loop has made no step for longer than its bound: 60 seconds, plus the poll interval, plus the longest time one step can take (the longest transform timeout, HTTP destination timeout, or twice an MLLP destination's ACK timeout plus a second). A source that cannot listen or a destination that is down never makes it 503, so a restart policy pointed at it does not restart an engine that a restart would not fix.
  - `/readyz` is 503 `starting`, `standby`, `draining` or `fenced` (the engine lost its lease) while the engine is in that state, and 503 `unavailable` when storage cannot be read or a source cannot listen. On SIGTERM or SIGINT it turns 503 `draining` at once, while the sources close, and the listener closes last.

  - New command: `pathways probe [--ready] [--if-configured]` asks the probe listener and exits 0 or 1, reading at most 256 characters of the answer. With `--if-configured` it exits 0, asking nothing, when `pathways.yaml` has no `probes` block.

With a `probes` block the check asks `/livez`; without one it passes, so an existing project turns `healthy`, not `unhealthy`, after the upgrade, whether it runs under plain `docker run`, as a Docker Swarm service (which replaces an unhealthy task) or behind Compose's `depends_on: condition: service_healthy`. Nothing for a caller to change; to leave the check out, run with `--no-healthcheck`.
  - `/livez` counts each channel of a retention run as a step. One channel's retention delete has no time limit, so a very large backlog past its retention period can still make `/livez` 503 `stalled` until it is done.
  - The health body gains `version`, `schemaGeneration` (`null` on a custom store), `node`, `role` (`active`, `standby`, or `single` on a store without leases), `leaseEpoch` (`null` unless held) and `draining`. A caller that compares the whole body with `toEqual` or a JSON schema that forbids extra keys must allow the new fields; the existing fields are unchanged.

- 2ce8637: `pathways rekey` now says when an older master key is safe to retire. On SQLite, once every value is

- 3b0f94d: Retries are now settings: a `retry:` block in `defaults:` in `pathways.yaml`, at the top level of a `channel.yaml`, or in one destination's block. The narrowest level that sets a key wins, key by key. Nothing changes for a project that sets none: the defaults are the waits Pathways used before, 1 second doubling to 5 minutes, with no jitter and no limit, in order.

  - `first` (default `1s`), `max` (`5m`) and `factor` (`2`) set the waits. `max` also caps what a `Retry-After` asks, and is how long a held redirect waits. A `first` longer than `max` is refused, naming the file and key.
  - `jitter: full` waits a random time between 0 and the capped wait, so several destinations sending to one receiver, or several engines, do not retry at the same moment. The default is `none`.
  - `limit` (attempts, the first included) and `maxAge` (counted from when the delivery was queued) end retrying; both default to `none`, which also lifts a limit a wider level set. At the limit or the age the delivery is marked failed with its body kept, so `pathways replay <id> --resend` can send it again, and the destination moves on. Its stored error names why, such as `exhausted (limit, 20 attempts): delivery: ECONNREFUSED`; the engine logs `delivery-exhausted`, hooks receive a new `delivery-exhausted` event, and the channel shows `failed` on health once nothing of it is retrying. `onExhaust: failed` is the only choice for now.
  - Every retry key may be read from the environment, `{ env: NAME }` or `{ env: NAME, default: value }`, as other settings can; `limit` and `maxAge` take `none` from a variable too.
  - `rotate: true` lets later deliveries go ahead of one waiting for a retry. It breaks the destination's order, so it is off by default.
  - New exports: the `DeliveryExhaustedEvent` and `NextDeliveryOptions` types, and `delivery-exhausted` in `LIFECYCLE_EVENTS`. A hook that lists its `events:` should add `delivery-exhausted` to hear of it; a hook that switches on every event type meets a new one.
  - For custom store implementers: `MessageStore.nextDelivery` takes an optional third argument, `{ dueBy }`, asked only for a destination with `rotate: true`. A store that ignores it keeps working, and keeps that destination in order.

- dbc2fb2: A schema gate, a migration lock and a `pathways migrate` command, with schema steps tagged expand or contract. Before, every engine start ran every missing schema step on a shared database, and an engine that met a schema a newer Pathways had moved forward failed with "the database schema could not be brought up to date", even when nothing it read had changed.

  - A new `schema_info` table, added by step `0007-schema-info` (expand only: a new table an older Pathways never reads), records each applied step with its generation, its tag, the oldest Pathways that may run on the schema once it is applied, the Pathways that applied it, and when. The step records itself and every step before it; each later step records itself in its own transaction.
  - When it opens a database, Pathways reads `schema_info` before Kysely's migrator runs. A schema missing expand steps gets them, under the migration lock; a schema a newer Pathways moved forward with expand steps opens as it is, with nothing applied; a schema a newer Pathways contracted past this version is refused, naming both versions (`the database schema is generation 9 and needs Pathways 0.3.0 or later; this is Pathways 0.2.0`), never a URL or a path. Contract steps are never applied at open.
  - The migration lock is Kysely's own, which holds across processes: a PostgreSQL advisory lock, MySQL's and MariaDB's `GET_LOCK`, or SQL Server's `sp_getapplock`, on the connection that runs the steps. On SQLite the steps run inside `BEGIN IMMEDIATE`. Engines that start at the same moment apply each step once.
  - CLI additions: `pathways migrate [--contract] [--dry-run] [--json]` applies the missing steps and prints each with its generation and tag. Expand steps always; contract steps only with `--contract`, and refused while the schema changed within the new `migrations.rollbackWindow` in `pathways.yaml` (default 0). Each run, a dry run and a refusal too, is written to the audit log as the new `migrate` action once the database has an audit log. It needs no encryption keys, and refuses a custom store. `pathways start --no-migrate` applies nothing and refuses, naming both versions, a database that lacks an expand step it needs.
  - `StoreOptions` addition: `migrate`, `"expand"` (the default), `"none"` (as `--no-migrate`) or `"inspect"` (apply and refuse nothing, as `pathways migrate` opens). `Store` gains `schema()` and `migrate()`. The audit actions, and `AuditEventAction` for hooks, gain `migrate`. A caller needs no change: a store opens as before unless a newer Pathways moved its schema.
  - Rolling back to 0.0.1: 0.0.1 does not read `schema_info` and knows steps `0001` to `0004` only, while this release applies `0005-send-markers`, `0006-leases` and `0007-schema-info` together to a 0.0.1 database. 0.0.1 refuses a database holding a step it does not know (`the database schema could not be brought up to date`), so take a backup before the first upgrade from 0.0.1: restoring it is the only way back to 0.0.1.   - Not covered yet: `pathways migrate --contract` does not see which versions other engines run, so stop or upgrade them before you contract. This version ships no contract step.

### Minor Changes

- 758e76f: The file source deletes each file once its message is stored, encrypted, instead of moving it into
  `processed/`. A run that stops between storing a file and deleting it stores that file once on

### Patch Changes

- 726e707: A configuration problem about the project folder itself names it `.`, as every other path in a
  problem is named relative to the project, instead of printing the full path the caller typed.
- 9a165ee: The file source takes a file whose name is as long as the file system allows: a claimed file's
  name is a fixed-length claim id and as much of the end of its own name as fits in 255 bytes, and a
  `processed/` copy's name fits the same way. The moves that claim a pass's files are flushed to disk
  before any of them is stored, so a power cut cannot put a stored file back in the folder to be
  stored again. Each channel claims into `.claimed/<channel>/`, so two channels that read one folder
  never finish each other's files.
- 5c06538: The file source works on Windows. Windows cannot flush a folder to disk, so there each pass flushes
  every file it claims, under its claimed name, before it stores any of them, in place of the
  folders Linux and macOS flush. On Windows a file is opened to write before it is claimed, so a
  read-only file stays where it is and is reported as a read error. Linux and macOS are unchanged.
- 726e707: The engine ignores a message a transform posts itself from its worker thread. Before, a transform
  that posted `null` or `undefined` through `parentPort` threw in the engine's own thread, and only
  the worker's reply for the message now settles it.
