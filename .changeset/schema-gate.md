A schema gate, a migration lock and a `pathways migrate` command, with schema steps tagged expand or contract. Before, every engine start ran every missing schema step on a shared database, and an engine that met a schema a newer Pathways had moved forward failed with "the database schema could not be brought up to date", even when nothing it read had changed.

- A new `schema_info` table, added by step `0007-schema-info` (expand only: a new table an older Pathways never reads), records each applied step with its generation, its tag, the oldest Pathways that may run on the schema once it is applied, the Pathways that applied it, and when. The step records itself and every step before it; each later step records itself in its own transaction.
- When it opens a database, Pathways reads `schema_info` before Kysely's migrator runs. A schema missing expand steps gets them, under the migration lock; a schema a newer Pathways moved forward with expand steps opens as it is, with nothing applied; a schema a newer Pathways contracted past this version is refused, naming both versions (`the database schema is generation 9 and needs Pathways 0.3.0 or later; this is Pathways 0.2.0`), never a URL or a path. Contract steps are never applied at open.
- The migration lock is Kysely's own, which holds across processes: a PostgreSQL advisory lock, MySQL's and MariaDB's `GET_LOCK`, or SQL Server's `sp_getapplock`, on the connection that runs the steps. On SQLite the steps run inside `BEGIN IMMEDIATE`. Engines that start at the same moment apply each step once.
- CLI additions: `pathways migrate [--contract] [--dry-run] [--json]` applies the missing steps and prints each with its generation and tag. Expand steps always; contract steps only with `--contract`, and refused while the schema changed within the new `migrations.rollbackWindow` in `pathways.yaml` (default 0). Each run, a dry run and a refusal too, is written to the audit log as the new `migrate` action once the database has an audit log. It needs no encryption keys, and refuses a custom store. `pathways start --no-migrate` applies nothing and refuses, naming both versions, a database that lacks an expand step it needs.
- `StoreOptions` addition: `migrate`, `"expand"` (the default), `"none"` (as `--no-migrate`) or `"inspect"` (apply and refuse nothing, as `pathways migrate` opens). `Store` gains `schema()` and `migrate()`. The audit actions, and `AuditEventAction` for hooks, gain `migrate`. A caller needs no change: a store opens as before unless a newer Pathways moved its schema.
- Rolling back to 0.0.1: versions before this one do not read `schema_info`, and refuse a database this version or a later one has opened (`the database schema could not be brought up to date`). Take a backup before the first upgrade from 0.0.1; to go back, restore it, or remove the `0007-schema-info` row from `kysely_migration` and drop `schema_info` by hand. Going back to the version before, on a schema holding only expand steps, holds from this version on.
- Not covered yet: `pathways migrate --contract` does not see which versions other engines run, so stop or upgrade them before you contract. This version ships no contract step.
