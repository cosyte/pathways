"@cosyte/pathways": patch

A channel's transform module may export `onStart` and `onStop`, each message gets one `settled` event, and `pathways start` records its starts and stops in the audit log.

- New: `export const onStart: OnStart` and `export const onStop: OnStop` beside a transform's default export. `onStart(ctx)` runs in the channel's worker before it takes a message, on every new worker (at start, on a reload, under `pathways test`, `replay` and `verify`, and in the worker that replaces one after a timeout, a memory cap or a crash), so it must be idempotent. `ctx` holds `channel`, `config` and a `logger` that takes a code and numbers only. `onStop()` runs before a worker ends on a clean stop (`SIGTERM` and `SIGINT` among the ways, and a reload) and is cut at its limit. Both have a new setting, `scriptTimeout`, the transform `timeout` unless set. These scripts are user code with the worker's full Node.js access, not a sandbox.
- An `onStart` that throws or runs past its limit is a load failure: the start stops, or a reload is refused. In a replacement worker, that channel stops, the health endpoint answers 503 with `transform: { loaded: false, kind, name, code }` for it, and the other channels run on until `pathways channel reload` loads it. Before, a transform that would not load in a replacement worker ended the whole run.
- New lifecycle event `settled` (`SettledEvent`), once per message when its last delivery is delivered or failed for good, or it was filtered, or its transform failed, with the message id and each destination's `{ index, name, state }`. It is recorded on the message's row by one conditional update, so a restart sends one the last run did not record and nothing is sent twice; a replay or a resend settles again. `LIFECYCLE_EVENTS` gains `settled`: a hook that switches on every event adds a case for it.
- Schema step `0012-settled` adds `messages.settled_generation` (expand only) and marks every message that had already ended as settled, so none of them gets an event. A custom store (`storage.module`) may implement the new optional `settle` and `unsettled`; one without them runs as before and sends no settled events.
- `AuditAction`, `AUDIT_ACTIONS` and `AuditEventAction` gain `engine-start`, `engine-stop` (each with `version`, `channels` and `node`) and `unclean-shutdown` (written at a start when the run before left no `engine-stop`). A hook or tool that switches on every audit action adds cases for them. A hook on `engine-start` is how a project runs a step once a deployment is up; there is no project-wide deploy script.
- Hooks stay best effort: past 1,000 waiting events for one hook new ones are dropped, and the audit log and the message states are what to count from where every one matters.
