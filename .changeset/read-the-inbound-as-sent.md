A channel can now repair, decode and pass through what its senders actually send, while the body it stores stays the bytes as received.

- `preprocess:` in `channel.yaml` names a module whose default export takes each body's bytes before they are decoded, with `(bytes, info)`, and returns the bytes or the text to decode. It runs in the channel's transform worker under the transform's `timeout` and `memory` limits. A throw fails the message at the new `preprocess` stage with its error's code or `PREPROCESS_FAILED`, an empty result with `PREPROCESS_EMPTY`, and any other result with `PREPROCESS_INVALID`; logs and events carry the code, never the body. What the preprocessor returns is not stored, and a replay runs it again.
- `encoding:` (`utf-8`, `latin1` or `windows-1252`) says what character set an `hl7v2` or a `text` channel's bodies are in. On `hl7v2` it is `@cosyte/hl7`'s charset override, so it wins over MSH-18 for a sender known to mislabel its bytes. `latin1` is ISO 8859-1, byte for byte, not the windows-1252 mapping `TextDecoder` gives that label. An `hl7v2` channel with `windows-1252` refuses to start with `ENCODING_UNSUPPORTED` on an `@cosyte/hl7` that cannot decode it, rather than read 0x80 to 0x9F as Latin-1; a `text` channel reads it itself. Every other format takes no `encoding` and stays strict UTF-8, and `text` without one stays lenient UTF-8, so nothing changes for a channel that sets none.
- `parse:` on an `hl7v2` channel passes `{ strict, trimFields }` to `@cosyte/hl7`'s parse options. Any other key is refused when the configuration loads.
- When an `hl7v2` parse raises `ENCODING_MISMATCH`, `UNKNOWN_CHARSET` or `UNSUPPORTED_CHARSET`, the engine stores the codes with the message, counts them by code on the health endpoint under the channel's `warnings`, and logs `inbound-warning` with the channel, the message and the codes. `pathways messages show` prints them.
- `format: raw` hands the transform a copy of the body's bytes as a `Uint8Array` and sends the bytes it returns: `.bin` on a file destination, `application/octet-stream` on HTTP.
- Schema step `0011-message-warnings` (expand) adds the column `messages.warnings`, which may be null and holds codes only. It only adds, and has no rollback step.
- New in the API: the types `Preprocess`, `PreprocessInfo` and `InboundEncoding`; `raw` in `Format`, `MessageTypes` and `MessageFor`; `preprocess` in `TransformFailureKind`; the optional `MessageStore.recordWarnings(messageId, codes, epoch?)`; and the optional `warnings` on `MessageSummary`. A custom store needs no change: without `recordWarnings` the engine still counts and logs each warning and stores none. Code that switches over `Format` or `TransformFailureKind` gains one case to handle.
