A transform and a filter per destination.

- A destination block takes three new keys: `transform:`, its own transform module; `name:`, unique in the channel (lowercase letters, digits and hyphens); and `format:`, the format the destination sends, the channel's by default. A destination's `format` sets the extension a file destination writes and the `Content-Type` an HTTP destination sends.
- A destination's transform runs in the channel's worker, in the same pass as the channel's transform and under its one timeout and memory cap: once for each channel output, which it reads parsed in the channel's format, and what it returns is written in the destination's format. It returns a message, several, or `null` to filter that destination for that message. Its context is the channel transform's with `ctx.destination`: `{ index, name, kind }`, typed by the new exported `DestinationFacts`. A destination transform that will not load stops the channel's start, and `TransformLoadError` names the destination in its new `destination` field.
- A new delivery state, `filtered`: the destination's transform returned nothing, so nothing is sent to it. It is done, as a delivered one is, for a message's state, for dropping content after delivery and for retention. When every destination filters a message, the message is `filtered`. A throw in a destination's transform fails that destination's delivery only, with its error stored through the codec, encrypted under encryption, and never logged (a `destination-transform-failed` log event carries its kind, name, code and where); the other destinations go on.
- `pathways replay` runs the channel's and every destination's transform as they are now; `pathways replay --resend` sends each destination the bytes stored for it, even after its transform changed, and never another destination's: a destination added since the message's last transform is sent nothing, and the command and the `resend` audit entry count it (`not-stored`, `notStored`). `pathways verify` runs the destination transforms and compares each destination with the outputs stored for it, or with its own sample file, named as `pathways test` names it; a destination with nothing stored is counted as `not-stored` and not compared.
- Each delivery records the destination it was made for by its identity: its `name:`, or, without one, its kind and target (a folder, a URL, a host and port, a module), kept as a hash in a new `deliveries.destination_key` column (schema step `0012-destination-keys`, an expand step: a column that may be null and an index; numbered after `0011-delivery-failed-at`). The engine's queue, a resend, `pathways verify` and `pathways messages show` find each destination's deliveries by it, never by the destination's place in `channel.yaml`'s list, so adding a destination anywhere, removing one or reordering them never sends, resends or compares one destination with another's outputs. That needs each destination's identity to be its own: `pathways validate` and a start refuse a channel with two destinations that have no `name:`, the same kind and the same target, naming both (`destinations.2: sends where destinations.0 sends, and neither has a name:`), and ask for a `name:` on each. At a channel's first delivery pass the engine holds the pending deliveries none of its destinations was made for, logged as `deliveries-held` with a count: one made for a destination the channel no longer has (`destination-gone`) stays pending, and is sent if it comes back; one queued before this release, which records no destination (`destination-unknown`), is marked failed with the error `delivery: destination-unknown`, so its message can be replayed. A resend of a message stored before this release is refused with the new `ActionRefusal` `destination-unknown`; a replay runs it again. Renaming a destination, setting a `name:` on one without, or changing the target of one without a name makes it a new destination: give each destination a `name:` when you add it. `pathways test` compares one expected file per destination on a channel with destination transforms, `<input>.expected.<destination name, or its place from 1>.<extension>`, and a missing file expects that destination to filter the input out. `pathways messages show` lists a filtered delivery and each destination's name; `pathways status` counts filtered deliveries.

The public API additions: the `transform`, `name` and `format` keys and the `DestinationConfig` fields of the same names; `DeliveryStatus` gains `filtered`, and `DeliveryCounts` and `DeliveryTally` an optional `filtered` count; `DestinationFacts` and `TransformContext.destination`; and a store change, with the new `DestinationOutcome` and `TransformOutputs` types. A storage adapter's `completeTransform` may now be given `{ byDestination }`, one `DestinationOutcome` per destination, in place of the list of outputs; a `RequeueRequest` may carry `byDestination` in place of `outputs` for every destination, where a resend gives a destination with nothing stored `{ notStored: true }`, which writes no delivery, and `RequeueResult` and `ReplayResult` gain an optional `notStored` count; and `outputs(messageId, destination?)` takes the destination to read, by its place or, as the new `DestinationKey` `{ key }`, by its key. `completeTransform` takes a fifth argument, `keys`, each destination's key in order, and `RequeueRequest` a `keys` field: storage records each on its deliveries, and the built-in `Store` refuses `{ byDestination }` without them. `NextDeliveryOptions` gains `key`, so the engine claims the deliveries made for a destination wherever it stands; `StoredDelivery` gains `destinationKey`; and `MessageStore` gains the optional `holdDeliveries`, returning the new `HeldDeliveries` counts. A destination with no output is written as one delivery with `seq` -1, `filtered`, or `failed` with its error. What a caller must change: a channel with two unnamed destinations of one kind and target, such as one `module` destination listed twice with different `options`, gives each a `name:`; and a project with its own storage adapter handles the store change. A storage adapter handles the changes above, as the built-in `Store` does; one that ignores `keys` and `key` still runs, finding deliveries by place as before, but a resend through it is refused as `destination-unknown`, since its deliveries record no destination. Before upgrading a project whose database has pending deliveries, let them deliver, or replay their messages after the upgrade.
