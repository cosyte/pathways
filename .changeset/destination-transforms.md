A transform and a filter per destination.

- A destination block takes three new keys: `transform:`, its own transform module; `name:`, unique in the channel (lowercase letters, digits and hyphens); and `format:`, the format the destination sends, the channel's by default. A destination's `format` sets the extension a file destination writes and the `Content-Type` an HTTP destination sends.
- A destination's transform runs in the channel's worker, in the same pass as the channel's transform and under its one timeout and memory cap: once for each channel output, which it reads parsed in the channel's format, and what it returns is written in the destination's format. It returns a message, several, or `null` to filter that destination for that message. Its context is the channel transform's with `ctx.destination`: `{ index, name, kind }`, typed by the new exported `DestinationFacts`. A destination transform that will not load stops the channel's start, and `TransformLoadError` names the destination in its new `destination` field.
- A new delivery state, `filtered`: the destination's transform returned nothing, so nothing is sent to it. It is done, as a delivered one is, for a message's state, for dropping content after delivery and for retention. When every destination filters a message, the message is `filtered`. A throw in a destination's transform fails that destination's delivery only, with its error stored through the codec, encrypted under encryption, and never logged (a `destination-transform-failed` log event carries its kind, name, code and where); the other destinations go on.
- `pathways replay` runs the channel's and every destination's transform as they are now; `pathways replay --resend` sends each destination the bytes stored for it, even after its transform changed, and never another destination's: a destination added since the message's last transform is sent nothing, and the command and the `resend` audit entry count it (`not-stored`, `notStored`). `pathways verify` runs the destination transforms and compares each destination with the outputs stored for it, or with its own sample file, named as `pathways test` names it. `pathways test` compares one expected file per destination on a channel with destination transforms, `<input>.expected.<destination name, or its place from 1>.<extension>`, and a missing file expects that destination to filter the input out. `pathways messages show` lists a filtered delivery and each destination's name; `pathways status` counts filtered deliveries.

The public API additions: the `transform`, `name` and `format` keys and the `DestinationConfig` fields of the same names; `DeliveryStatus` gains `filtered`, and `DeliveryCounts` and `DeliveryTally` an optional `filtered` count; `DestinationFacts` and `TransformContext.destination`; and a store change, with the new `DestinationOutcome` and `TransformOutputs` types. A storage adapter's `completeTransform` may now be given `{ byDestination }`, one `DestinationOutcome` per destination, in place of the list of outputs; a `RequeueRequest` may carry `byDestination` in place of `outputs` for every destination, where a resend gives a destination with nothing stored `{ notStored: true }`, which writes no delivery, and `RequeueResult` and `ReplayResult` gain an optional `notStored` count; and `outputs(messageId, destination?)` takes the destination to read. A destination with no output is written as one delivery with `seq` -1, `filtered`, or `failed` with its error. What a caller must change: nothing, unless the project has its own storage adapter and a channel with a destination transform; such an adapter handles the changes above, as the built-in `Store` does. A channel without destination transforms calls a store exactly as before.
