A channel can store no message at all: with `storage: { content: none }`, each message is transformed and sent to every destination while its sender waits, and the source answers only once every destination accepted it.

- New channel keys: `storage.content: none` and `storage.passTimeout` (a duration, 30 seconds by default), which bounds how long a sender waits for its answer. Only a channel sets `none`: `pathways.yaml`'s `storage.content` still takes `keep` or `dropAfterDelivery`, and `passTimeout` is refused without `none`. Nothing changes for a channel without them. At start the engine logs `content-none` for each such channel.
- What the sender is told: MLLP answers `AA`, HTTP its usual 2xx, and a file source deletes or moves its file, only once every destination accepted the message. A destination that fails or times out, or a pass past `passTimeout`, leaves the sender to send again: no ACK over MLLP (as `onStoreFailure` says, by default a closed connection), 503 with `Retry-After` over HTTP, and the file stays for the next pass. A transform that fails, or a destination that rejects the message for good, is answered `AE` over MLLP, 422 over HTTP (an `AE` ACK with `response: ack`), and the file moves into `errorDir`.
- Nothing is kept to replay: no body, output or delivery is stored, so there is no replay, resend, retry queue, rekey or retention for such a channel. A crash before the answer leaves the sender unanswered, so nothing it was told was received is lost; a duplicate comes from its retry. Messages pass one at a time per channel, in order.
- A file source on such a channel needs `errorDir`, and an S3 or Azure Blob source cannot store nothing yet: `pathways start` refuses either.
- Each message on such a channel gets a pass id, the time it came in, in microseconds since 1970, and never given twice while the clock does not go back: it is the `messageId` destinations name their outputs by, `sink.receive` resolves with it, and a file source's `keepProcessed` copy is named by it. A restart gives higher ids, so a file, S3, Azure Blob or email destination never overwrites or reuses a name an earlier run used. A caller that read the id as a count of messages should not.
- The health endpoint shows such a channel with `storage: "volatile"` and `passes` (`accepted`, `filtered`, `unreadable`, `rejected`, `deferred`), counted in memory since the engine started.
- New export: `PassFailed`, which `sink.receive` rejects with on such a channel; its `permanent` says whether the sender should send again, and `retryAfterMs` how long it might wait. A custom source needs no change: one that does not know it treats it as any failed `receive`. `CONTENT_POLICIES` gains `none`, and `PROJECT_CONTENT_POLICIES` and `DEFAULT_PASS_TIMEOUT_MS` are new in the configuration schema module. An MLLP ACK builder can be asked for a new `AckReason`, `rejected`, with code `AE`; a builder that switches on `reason` should handle it. A file source's `FileFaultReason` gains `rejected`.
- New log events `passed`, `pass-filtered`, `pass-unreadable`, `pass-transform-failed`, `pass-rejected`, `pass-deferred`, `pass-failed`, `poll-deferred` and `mllp-pass-rejected`, each with ids, counts and codes only. New docs page "Pass messages through without storing them"; the configuration reference, the codes page, the health page and the MLLP and HTTP pages say what changes.
