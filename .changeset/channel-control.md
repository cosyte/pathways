Control one channel of a running engine: `pathways channel pause`, `resume`, `stop`, `halt` and `reload`, without restarting the others.

- New command `pathways channel <pause|resume|stop|halt|reload> <name>`, with `--deadline` for `stop` and `halt` and `--json`. `pause` stops the source taking messages in while stored messages go on to delivery; `stop` also ends the channel's work after the message in hand, waits up to the deadline (30s by default) and reports what it left; `halt` cuts the delivery in flight off at once, leaving it pending to be sent again, flagged, after a `resume`; `reload` loads the channel's transform, its settings and the transform's `config:` blocks in a fresh worker and swaps them in between messages. A reload is refused, keeping the running transform, when the configuration is invalid or a `config:` value names an environment variable that is not set, the new transform throws as it loads, the channel is gone, a stop is still draining it, or the change is to the source, destinations, format or hooks (named, as needing an engine restart). Two reloads run one after the other.
- `pathways start` listens on a control socket: a Unix socket named by a hash of the project path in a `pathways-<uid>` folder it makes with mode 0700 (under `XDG_RUNTIME_DIR`, the temporary folder, or `/tmp`, within the socket path limit), or a named pipe on Windows. A stale socket is removed; a start that finds another engine answering there refuses and exits 1. One line of JSON each way, with a version, a 4 KB request limit and a 5s idle limit; replies carry states and counts, never content. `pathways channel` says `engine not running` when nothing answers.
- Paused and stopped channels are kept in a new `channel_states` table (migration `0008-channel-states`, an expand step, a new table only, on SQLite and the four servers), read at the top of each pass by every engine on the database: a restart keeps a channel paused, and a command given to one engine reaches the others within one pass. Dropping the table with every engine stopped sets every channel running. The engine changes the channel before it stores the state, so a stop takes hold at the next message; a state the database does not store is put back, and the command is refused as `state-not-stored`.
- Each command is written to the audit log as `channel-pause`, `channel-resume`, `channel-stop`, `channel-halt` or `channel-reload`, with the user the command reports; the socket folder, open to that user alone, is the trust boundary.
- The health body gains each channel's `state` (`running`, `paused` or `stopped`); neither paused nor stopped changes the answer from 200.
- API additions: `MessageStore` gains the optional `channelStates` and `setChannelState` (a custom store without them keeps a channel's state in the engine only, and a restart forgets it); `OutgoingMessage` gains an optional `signal`, aborted on a halt, which a custom destination may pass to its client; new exports `ChannelRunState` and `ChannelStateStore`. `AuditAction` gains the five channel actions. No caller needs to change.
- New log events: `channel-state`, `channel-states-unread`, `channel-state-unstored`, `channel-reloaded` and `delivery-halted`.
