A channel can make `ctx.meta` keys searchable, and `pathways messages --where key=value` finds messages by them.

- A new `index:` block in `channel.yaml` names `ctx.meta` keys, each alone or as `{ key, bits }` (`bits` 4 to 32, default 12). For each indexed key a message's metadata holds, the store keeps a tag: the HMAC-SHA-256 of the value as text, cut to its first `bits` bits, under a key derived with HKDF-SHA-256 from the current master key, the channel and the index name, with the master key's id beside it. Equal values give equal tags, so the tags show which messages may share a value (one patient's messages all carry the same tag), while other values can share a tag too, about `d / 2^b` of them with `d` distinct values in the channel; a search reads each row with the tag, decrypts its metadata and keeps only the rows that hold the value. Values are compared exactly as stored text: case, surrounding spaces and Unicode form all count, so normalize a value before storing it. With `b` bits, a search reads about one row in 2^b of the channel's rows that it then drops: one in 4,096 at the default.
- `pathways validate` and `pathways start` warn about an index on a key whose name says its values are few or guessable (sex, status, a birth date and the like), and still run it. An `index:` block under `encryption: none` is a configuration error.
- `pathways messages --channel <name> --where key=value` (repeatable, every pair must hold) lists the matching messages with the other filters of `messages`. It searches under every master key id the provider holds, reads at most 10,000 rows a page, and writes a `search` audit entry with the keys and filters, never the value, before it reads any row; it does not search when the entry cannot be written. A key the channel does not index is a usage error.
- `pathways rekey` re-encrypts each message's metadata under the current key and derives its tags again from it under the current key and the channels' `index:` blocks, so it also tags messages stored before an index was added. It prints how many messages it retagged when any.
- Message metadata is stored encrypted, like the body. In this release nothing in the engine sets `ctx.meta` yet; metadata is stored when the code that stores a message passes it.
- Schema step `0010-message-meta` (expand) adds a `meta` column to `messages` that may be null, and a `meta_index` table. It only adds, and has no rollback step. Retention deletes a message's tags with it, and `storage.content: dropAfterDelivery` clears a message's metadata and deletes its tags when it drops the content, so such a message can no longer be found by metadata.
- New in the API: `MessageMeta`, `MetaTag`, `MetaCondition`, `MetaCandidate`, `MetaCandidateQuery`, `StoredMeta` and `MetaStore`; the optional `meta`, `storedMeta` and `metaTags` on `StoreReceiveOptions`; the optional `ids` on `MessageQuery`; the optional `MessageStore.metaCandidates`; the optional `keyIds` and `deriveIndexKey` on `KeyProvider`; and `retagged` on `RekeyCounts`. A custom store needs no change: without `metaCandidates` it cannot be searched by metadata. A custom key provider needs no change unless a channel has an `index:` block: then it implements `deriveIndexKey`, and `pathways start` refuses the block on a provider without it.
