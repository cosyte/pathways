One message per idempotency key, even when it is handed in twice at the same moment.

Two hand-ins of one message under one idempotency key at the same moment, on two connections or two nodes, could both be stored on PostgreSQL, MySQL and MariaDB: each inserted its row and then looked the key up, and neither saw the other's row before it committed. (On SQL Server the second lookup already waited for the first row, at its default locking read committed.) Now each message claims its key in the same statement that inserts it, in a new `messages.idempotency_claim` column that a unique index covers (`messages_by_channel_idempotency_claim`, schema step `0014-idempotency-claims`, an expand step numbered after `0013-destination-keys`). The second insert waits for the first's transaction and yields to its row, so a resumed hand-in gets that message's id back with `alreadyStored` and nothing new is stored. This holds on SQLite, PostgreSQL, MySQL, MariaDB and SQL Server, each at its default isolation level. A hand-in that is not resumed is still always stored, without the claim when another message holds it. A resumed hand-in whose claim is free still looks for an earlier message under its key, so it finds one stored before this release, or by an older Pathways beside it.

The schema step gives each key's claim to the earliest message of its channel stored under it. A database that already holds two messages of a channel under one key keeps both, each with its body, status and deliveries; only the earliest holds the claim, and a resumed hand-in finds that one, as before. To roll the step back, stop every engine and drop the index and the column.

An id a server spent on an insert that yielded is not used again, so message ids can skip a number after a hand-in that found its message stored. A retention archive now carries `idempotencyClaim` with each message; an archive written before this release has none and still opens. `StoredMessageRow` gains `idempotencyClaim`: a store wrapper that builds those rows itself sets it, `null` when it keeps no claims. Nothing else a caller must change. A custom `MessageStore` that more than one connection writes to should make its key lookup and insert one atomic step, as the `MessageStore.receive` documentation now says.
